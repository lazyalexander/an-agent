# Weaver and independent spool development

Weaver is an optional domain-task preparer and candidate reviewer, exposed by
Loom through replaceable harness adapters. Domain requirements and tests stay in
the project. Loom owns development baselines, checks and packaging; the host owns
runtime authority, supervision, context access and accepted state/products.

A spool may expose its own CLI for zero-mount development without an-agent.
Standalone checks and offline packaging do not imply sandboxing, termination
evidence or host acceptance. Do not treat local success as a host receipt.
Formal platform-managed agents must be admitted and activated under an-agent:
selected release and instance, effective grant, supervised attempt and acceptance.
The current native route provides load plus separately approved start; this does
not claim a general agent activation registry. Loading alone grants no execution.
A public executable can still be run independently by its owner.

Select exact domain materials, retain provenance and distinguish original rules
from assumptions. A developer reviews the specification and acceptance contract
before dispatch to a coding tool. Changing those selected bytes requires a new
review/task. A specification approval grants neither execution nor permission to
send private materials to a provider. Independent model/provider and execution
approvals remain host responsibilities where the host is used.

The host does not evaluate domain truth. Weaver proposes rules and review
findings; the developer resolves ambiguity. The existing kit-proposal slot only
admits scoped edits and is not the Weaver preparer. Hooks cannot widen grants.
External harnesses retain their own context/tape; selected requests, code and
boundary evidence are sufficient without importing their private sessions.

Follow the Loom-side Weaver contract and qualified example. No domain-specific
parser, model loop, knowledge-base service or new backend belongs in core.
