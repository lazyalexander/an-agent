# an-agent — 工作协议

[English](../../AGENTS.md) · 中文译文，以英文为准。 · [中文目录](README.md)

本文件是本仓库中所有代理遵循的规范。它之所以比设计文档更短，是因为它涵盖了代码的流动，而不是代码的含义。对于公共架构和实现契约，从[`doc/README.md`](doc/README.md)开始，遵循链接的契约。私有协作/设计笔记是补充性的，不能复制到公共仓库中。

## 项目语言

代码注释和示例代码保持英文。英文文档具有权威性。简体中文文档作为翻译保持一致。与用户交流遵循用户的语言。

## 分支线

- `main` — 稳定分支。仅接收来自`dev-advance`的批量合并，以PR形式打开，并由用户合并。
- `dev-advance` — 唯一的开发权威。每个功能PR目标此分支。绝不从`main`分支新工作。
- `dev-*` — 特性分支。本地优先；仅在需要PR的头部时推送。

规则：

- 代理在审核差分后，可将PR合并到`dev-advance`，完成适用的本地/真实接受，并通过所选头部的每个CI门。若有疑似私有数据、凭证、会话记录或发布范围不明确的材料，必须由用户审查后才能发布或合并。禁止绕过门禁。
- 每次开发合并后，需通知用户，包含仓库、PR、目标分支、结果提交和简短描述。主推广仍需用户决策和合并；开发授权不扩展到主分支。
- 保持每个PR的范围。交接后，仅添加修复或评审回应，不添加无关功能。独立工作分支从当前开发分支；依赖的后续可能保持本地，其基础PR/提交记录，然后基于验证后的合并开发前发布。避免长堆叠链条。
- PR基础为`dev-advance`，而非其他特性分支。如果后续依赖未合并的PR，正文中标注"stacks on #N" — 当#N合并时，重新指向（`gh pr edit M --base
  dev-advance`）。将堆叠PR合并到其堆叠基础会从权威线移除工作；此事故已发生两次（#42, #44），每次成本一次同步PR。
- 远程分支管理。远程持有`main`、`dev-advance`，以及进行中的 PR 分支。删除一个头部当其PR合并（`git push origin --delete <branch>`）。本地分支可自由保留。
- 本地清理仅删除超过7天的分支，已合并到开发且未在任何工作区检查出的分支。保留main/dev-advance和未合并的工作；验证祖先并使用安全删除。不得仅为了清理分支而分离工作树。
- 任何预期合并到`dev-advance`的合并后，需验证与`git log origin/dev-advance --oneline -5`，确认确实如此。不信任PR页面。

## 资产测试（可能走向主分支的案例）

一个案例通过它在死亡时留下的东西获得其位置：

- **资产** — 留下运行时机制、已发布的spool体和标准`cargo test`覆盖，这些测试真实内核路径（AgentControl, register, mount match, dispatch, tape）。资产通过功能 PR 进入`dev-advance`和后来的`main`。示例：`an-agent-spool/tests/discord_parley.rs` — 其脚本出站可替换为真实桥，而无需改动它证明的链。
- **探针** — 只留下骨架：并行套件、重复的mount路径、单次粘合。探针必须永远不进入主分支。示例：退役的`an-agent-probes` crate — 它在内核旁运行，而非通过它，删除它成本为零。

## 实验室（实验和观察工具集）

- 实验和观察/辅助工具集位于顶级目录 `lab/` 下的专用包中，这些包被忽略在 Git 中 —— 它们永远不会合并到 `main`。
- 实验包的路径依赖于工作区包；工作区包从不依赖实验室包。单向依赖，因此实验室可以始终被删除而不影响产品。
- 实验代码可能有脏状态。它未经过产品标准审查，也不默认推送到远程 —— 推送实验室工作是一项明确的、已声明的决策。
- 实验室不是工作区成员，因此 `dev-advance → main` 合并无法携带其内容。
- 推荐是重新实现，而不是合并：将已验证的干净想法在正确的 crate 中重写，并通过测试，然后删除实验室原始代码。

## 将一批内容整合到主分支

1. 所有该批内容的特征 PR 已合并到 `dev-advance`；行运行干净（见以下验证）。
2. 打开一个 PR `dev-advance → main`，说明该批内容。用户进行合并。
3. 合并后，确认 `origin/main` 和 `origin/dev-advance` 一致，并清理该批的远程头。

## 每次提交前的验证

1. `cargo test --workspace` — 绿色。
2. `cargo clippy --workspace --all-targets` — 无警告。
3. `cargo fmt --all` — 已应用。
4. `cargo arch` — 与目标分支绿色对比。不要重置或提升基准线，以使功能通过。详见 [质量门](doc/quality.md)。

架构检查器是一个独立的 Cargo 工作区。产品工作区检查和 `cargo arch` 不会运行自己的测试。在每次 PR 推送前，也应运行：

- `cargo fmt --manifest-path tools/archcheck/Cargo.toml -- --check`
- `cargo test --manifest-path tools/archcheck/Cargo.toml --locked`
- `cargo clippy --manifest-path tools/archcheck/Cargo.toml --all-targets --locked -- -D warnings`

此外，还要执行领域特定检查：

- 该变更属于产品、案例资产还是实验室？将其放入这三个中的一个。
- PR 基础是否是 `dev-advance`？
- 模块拆分遵循拆分纪律（见 `split-modules` 技能）：拆分提交是一个纯粹的移动，公共路径保持不变，测试被移动而非丢失。

内容标签术语遵循 [spool 代码契约](doc/spool-code.md)。silk标签每个不可变的发布基线；套件标签可变衍生品和新工作。指令保持受保护；标签永不授予权限。保留遗留的 wire/API 名称，并区分目标契约与实现的运行时保证。

## 平台声明

在 [运行时矩阵](doc/platforms.md) 中维持当前支持，与 Loom 的工具集/移交矩阵协调。后端和专用文件系统适配器负责操作系统差异；接受入口点负责测试资格。保留历史的 profile ID 和证据不变。不要用跳过、回退或更广的授权来通过一个门。

## 测试所有权和语言

遵循 [测试契约](doc/testing.md)。保留用于内部不变量和故障窗口的 Rust 测试；优先使用 Python 对新黑盒 CLI/进程/文件接受；仅在浏览器集成从中受益时使用 TypeScript。现有 Rust 接受有效；选择性迁移，保持等价覆盖率。

宿主拥有生命周期、授权和产物保管保证。Loom 拥有撰写、打包和证据接收，配有狭窄的配对宿主烟雾测试。一次为选定的修订/目标/配置构建二进制文件，并将显式路径传递给外部套件；不要在每个场景内重新构建。

以上验证命令仍需执行。还需运行受影响的非Rust套件以及已文档化的实宿主验收测试，方可声称其保证。Cargo的成功 alone 不足以获得完全接受。迁移必须保留断言、取消/清理证据以及CI门禁，并且不能仅仅为暴露私有测试缝隙而添加生产调试API。应分别测量构建和执行过程；未知的执行结果不得自动重试。

## 文档所有权

保持架构、操作契约和公共资格配方在`doc/`中。一个包/目录的README提供方向、入口点和链接；它不能成为第二个契约或时间线进度日志。根`AGENTS.md`是贡献者指令的例外。在保留可执行的结构和必要的失败边界的同时，移除过时的计划和重复的说明。`documentation-policy.toml`设定文档数量/长度预算；`cargo arch`检查放置、预算和本地文件链接。在添加页面之前，应更新现有主题。预算增加或例外需要明确的审查理由，而非无声重置。保持公共`.gitignore`允许列表狭窄；不得发布忽略的私有笔记以满足链接检查。无通用的归档目录。
