## 有限的艺术品修订

此第一个配置文件检查点一个 UTF-8 文件，独立于 VM 保留。
Spools 携带领域知识和验证规则。宿主验证通用字节身份、血统和执行边界；它不判断编辑的业务正确性。Loom 作者/包发布；修订保管权属于宿主，不依赖于开发工具或 VM 生命周期。

### 操作员工作流程

从一个稳定的成功原生文件-kit 运行开始。`RUN` 表示其保留的运行目录，而不是 guest 工作目录。`CATALOG` 是一个独立的私有宿主拥有的目录；其父目录必须存在。`STORE` 仍然是执行存储。

```sh
an-agent-host artifact-import CATALOG RUN
## Record the returned revision as V1.
an-agent-host artifact-checkout CATALOG V1 editable.txt
## Edit and save editable.txt, then compute and approve its SHA-256.
an-agent-host artifact-edit CATALOG V1 editable.txt APPROVED_SHA256
## Record the returned revision as V2.
an-agent-host run-version STORE RELEASE CATALOG V1
an-agent-host run-version STORE RELEASE CATALOG V1 --execute
an-agent-host run-version STORE RELEASE CATALOG V2 --execute
```

使用 SHA-256 工具，如 `shasum -a 256 editable.txt` 在 macOS 上或 `sha256sum editable.txt` 在 Linux 上。批准的摘要为必填项：更改的字节将被拒绝，不会被静默采纳。这不会检测应用程序是否已完成逻辑上一致的保存；操作员或未来的 shuttle 必须提供该检查点。检出操作只会在外围目录中创建一个新文件，绝不会覆盖现有文件或锁定编辑器的工作副本。

`run-version` 当前选择本地后端，并使用现有的注册、AgentControl 接入、沙盒和产物接受路径。除非提供 `--execute`，否则它会预览；取消操作使用现有的 CLI 信号处理。现有的 `run` 和 `run-openshell` 命令保持不变。导入需要本地的 `STORE/runs/RUN` 目录和共享的 `settled_run` 网关，同时持有源存储锁。仅有成功的接收是不够的：接收、操作、终止观察、计划和最终结算/审计绑定必须一致。任何目录发布前，缺失或不一致的证据将被拒绝。不会合成缺失的证据，也不会重试任何运行。

此导入命令拒绝 OpenShell 和未知后端，直到它们拥有显式的宿主结算合同。OpenShell 的远程终止观察不能替代完成的宿主账本记录。其保留的输出仍可供检查；不会在该后端上强制本地标记文件，也不会从其接收中推断出这些文件。

### 身份和结算

每个修订 ID 是其精确清单字节的 SHA-256。清单绑定内容摘要、字节数、可选父级和源证据。内容身份和修订身份是不同的：相同字节但不同血统可能具有不同的修订。重新导入相同的检查点是幂等的；执行不会自动去重或重试。

一个新的导入的已接受运行源记录了运行ID、版本、接收摘要、验证结算标记以及对所选上游版本的有界引用。现有的目录修订版本仍可使用其原始ID进行读取；在更强的源证据合同下重新导入可能对相同内容生成一个新的修订版本。没有结算证据的旧运行无法导入。编辑记录其父项和一个操作检查点声明，而不是经过认证的人类作者身份。引用不会递归地嵌入整个历史记录或使数据成为受信任的指令。

宿主在每次读取时都会验证清单和内容哈希。新的基于修订版本的输入获取也会在读取前后检查单调闭合记录，而不排除其他读者。选择之后，该调用的精确字节会被保留，并复制到其现有的`input.txt`快照中。计划和接收记录`input_revision`；输入哈希继续使用实际的字节快照。新的编辑不会更改此输入，取消运行，使已完成的输出失效或安排下游工作。

```text
accepted output -> V1 -> downstream run bound to V1
                   |
             editable copy -> V2 -> another run explicitly bound to V2
                   |
             alternative edit -> V3 (may also name V1 as parent)
```

目前没有可变的最新指针，也没有自动合并。父引用支持独立分支；未来某个应用程序/卷轴可能会通过显式的前提条件提供合并语义。恢复旧字节并不是逆转外部操作、恢复进程或还原虚拟机。

### 存储和限制

`CATALOG/revisions/REVISION/{revision.json,content.txt}` 是一个私有的、由宿主拥有的检查点包。发布过程重用宿主独占写入、链接检查、有限读取以及协作写入锁。完整的包从私有的待发布目录发布；部分失败将被保留且永远不会被报告为已接受。读取操作不会选择待发布目录。崩溃后出现的过期锁需要操作员进行调查；没有自动恢复机制。

这个有限的配置文件重用现有的宿主存储原语，而不是添加第二个通用的工作区引擎。现有的 `an-agent-workspace` 可变树/HEAD/分支 API 不会被静默地采用作为产物来源合同。未来的存储整合可以保留这些清单和绑定语义。

- 产物内容和清单限制为 64 KiB；文本必须为 UTF-8。
- 现有的执行输入限制仍为 8 KiB。较大的有效检查点在创建运行之前被拒绝作为输入，不会进行截断。
- 失败、取消或未被已验收的输出不能作为已接受运行的修订版本。
- 被篡改的清单/内容、符号链接和硬链接将验证失败。
- 目录和运行存储是受信任的宿主存储，不可由工具包写入。哈希值可以检测针对选定身份的损坏，而不是针对整个存储的恶意同用户所有权。不声称文件系统不可变性或多用户服务。
- 保留是手动的。没有垃圾回收、独立备份、目录树版本控制、格式特定合并或断电恢复的承诺。

### 可重复接受

```sh

```

测试重用了实际的隔离文件-kit fixture（大写转换，带有文件系统/网络拒绝探针）。它执行 CLI 的导入、检出、编辑、预览和固定执行命令。它模拟了操作员的编辑：`ALPHA` 变为 `human beta`；V1 仍然产生 `ALPHA`，而 V2 产生 `HUMAN BETA`。之后的工作副本编辑不会改变任何版本。断言检查实际的输入快照、输出、收据绑定和内核应用的审计。其他情况拒绝损坏的源/目录、未接受的运行、链接文件、未批准的编辑、缺失的父项、无效的 UTF-8 以及超出限制的执行输入。

### 可选的不透明字节修订

工作区配置文件可以显式列出 `binary_outputs`，这是 `outputs` 的一个唯一子集。其他输出保持现有的 64 KiB UTF-8 合约。字节对象每个最多限制为 8 MiB，每接受项最多 16 MiB；它们的宿主拥有的修订清单使用 `an-artifact-revision-v2` 与 `content.bin`。现有的 v1 文本清单和身份保持不变。宿主不会检查扩展名、解析 Office ZIP 文件、评估公式或认证文档是否安全打开。

`artifact-checkout` 创建一个新的可编辑副本。`artifact-edit` 继承父项的存储格式，并仅提交批准保存的字节作为子修订。操作员的来源是声明，而非经过认证的人类作者身份。原始修订保持不可变；没有可变的 `latest` 引用。文本执行配置文件明确拒绝字节修订，即使它们的字节恰好是有效的 UTF-8。这不会扩大 `file-kit-v1` 或 VM 输出配置文件。

一个工作区可以分别声明 `artifact_inputs` 与 `path`、`catalog` 和一个确切的 `revision`。所选路径必须已经是声明的只读输入，且其字节必须与该修订匹配。目录保持为宿主专用；工作负载仅接收一个检查出的快照。批准绑定快照和不可变修订。发布重新检查原始输入和目录绑定。候选来源记录压缩修订/哈希/大小引用，而不是递归复制的转录或领域解释。

已取消、失败、未确认或被取代的尝试无法发布字节。
迟到的候选者不会修复已取消的接收记录。回收仍需要
已结算的证据和单独的批准；已接受的修订仍保留在草稿之外。
现有的本地可信所有权和非事务性多输出接受
限制仍然适用。内容摘要既不是发布者签名，也不是
独立的备份。测试涵盖了原生字节执行和篡改、保存
的编辑、固定下游消费、取消和迟到输出拒绝。

## 外部输入克隆：固定版本，无需完整负载复制

### 范围和决策

在现有的尝试快照准备中重用 macOS `fclonefileat`。
没有新增输入模式、spool API、全局目录、后端或 Loom 依赖。
普通选择的输入可能避免在兼容文件系统上进行完整的负载写入。
这是写时复制快照，而不是可变路径挂载、硬链接、零读哈希或零物理 I/O 的保证。现有的 64 MiB/文件和 100 MiB/计划限制保持不变。固定的艺术品输入保留其验证的目录路径。

[Apple syscall contract](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/clonefile.2)
描述了独立的 inode 属性和共享数据块、私有后续写入、独占目标创建和文件系统限制。克隆后仍可能耗尽磁盘容量。克隆支持并不能使不受信任的本地进程等同于虚拟机。

### 版本和权限边界

1. 现有的批准通过摘要识别选定的字节。
2. 打开源文件时不跟随其最终的符号链接，固定描述符，并检查常规文件类型、单链接和大小。源描述符在打开和克隆之间避免替换不同的 inode。
3. 仅限于克隆到现有的宿主拥有的尝试快照目录中。不要复制源文件的所有权或请求源文件 ACL 继承。
4. 验证目标文件与批准的摘要一致，应用只读模式并同步它。只有在完成这些步骤后，才发布解析后的执行清单并启动。
5. 工作负载仅接收快照占位符。原始选定路径仍被拒绝。接受性重新检查已保存的快照和清单证据。

在准备过程中，源文件的更改要么保留完全批准的快照，要么导致准备失败；仅有成功的克隆是不够的。之后的写入、截断、路径名替换和取消链接操作无法改变已接受的快照 inode。这并不能在独立更改的输入文件之间提供事务性，也无法防止恶意的同用户宿主管理员。

仅有 `EXDEV` 和 `ENOTSUP` 会回退到现有的有界复制。其他错误仍然保持为错误；预先存在的目标绝不会被覆盖。Linux 保留现有的复制实现，工作区执行配置文件仍为 macOS 专属。此次更改中没有引入新的 Linux reflink 或自动执行重试。

### 取消与保留

取消检查在准备之前、文件之间、克隆之后以及发布/启动清单之前进行。文件系统系统调用是同步的，并未声称其可抢占。现有的有界读取和哈希检查仍然保留；这不是一个新的取消延迟保证。失败或取消的准备保持现有的显式未启动结算路径，绝不会将部分快照作为可接受的产品提升。

在执行过程中，现有的作业锁和终止证据会阻止收集。未知终止会拒绝收集和输出接受。在确认终止后，显式回收会移除工作临时空间；成功结果必须首先被接受。**输入快照仍然保留尝试证据**，与之前相同。没有引入快照垃圾收集器或新的保留策略。删除克隆引用不会删除原始文件；删除原始文件不会释放仍被保留克隆引用的块。容量节省可能会随着源的变化而减少。

### 本地证据（2026-10-26）

真实的 macOS 宿主测试会写入 64 MiB 输入的每一个字节。五个案例分别测试就地覆盖、截断、路径名替换、解除链接和取消。工作负载在源被修改时等待，然后对快照本身进行哈希。检查包括不同的 inode、固定的摘要、运行时拒绝收集、缺少终止确认时拒绝收集、工作回收后接受输出检查，以及保留的输入证据。取消的尝试无法发布。额外的单元测试拒绝链接、过大输入、现有目标、预启动输入哈希变化以及缺失或替换的清单。

一个独立的本地文件系统探测器会写入完整的64 MiB和1 GiB文件，检查已分配的源块，调用相同的系统调用，并将其与流式完整复制进行比较。每个大小在温暖的本地存储上有三个观察结果：

| Size | Clone syscall ms | Full copy + sync ms | Initial SHA-256 read ms |
| --- | --- | --- | --- |
| 64 MiB | 0.103–0.135 | 8.299–12.671 | 23.707 |
| 1 GiB | 0.118–0.135 | 102.648–264.341 | 369.025 |

这些并不是端到端宿主时间，统计上隔离的基准测试或SLA。克隆列排除了后续的哈希计算、chmod和fsync；复制列包括流式读取/写入和fsync。开发测试使用调试二进制文件，不应与这些Python/OpenSSL哈希时间进行比较。1 GiB探测器仅验证文件系统行为，而不是在该大小下的宿主准入。它还检查在覆盖、截断和源文件解除链接后摘要的稳定性。

自愿启用的`AN_AGENT_HOST_TIMING=1`诊断会发出`snapshot_clone`，并带有`cloned`、`copy_fallback`或`error`。成功的克隆记录意味着在该路径上没有显式执行数据复制，而不是操作系统没有执行任何I/O。原始日志包含本地路径，并保留在私有观察输出中。观察脚本保留在被忽略的`lab/input-clones/`中；产品回归测试位于`tests/workspace_job/clone_handoff.rs`和相邻的快照单元测试中。

跨卷/不支持文件系统的回退功能在本切片的第二个本地卷中已指定但未验证。磁盘耗尽、崩溃耐久性和恶意进程逃逸均未由这些测量结果验证。在扩大任何这些声明之前，请保留现有的固定版本和终止门控。

## 已确定的工作回收和中介化制品读取

宿主拥有授权、已验收的产物身份和保留。一个spool拥有域计算和输出含义。一个后端强制执行执行限制并报告终止。Loom仍然是开发和打包工具；Loom和核心不需要为此配置文件引入新的API。

内部材料默认为可丢弃，但这并不意味着可以删除正在运行或状态不确定的环境。该首次实现特意被限制为原生 `file-kit-v1` 运行的两个工作文件。它不会回收虚拟机磁盘、任意临时文件树、任意失败运行、日志或制品目录。

### 重新回收前的证据

新的原生文件执行仅在收到、内核完成和审计已写入后才写入 `settled.json`。该标记将收到和审计摘要以及操作身份绑定在一起。它记录了宿主账本的完成，不一定表示执行成功。回收独立地需要以下所有条件：

- 匹配的运行和操作身份、有效的计划摘要，以及匹配的结算标记和审计摘要。
- 支持的原生文件后端、已回收的直接子项和明确的 `termination_confirmed: true`，且无任何 reconciliation 错误。
- 要么是成功退出并有单独接受的 `artifact.txt`，其摘要和长度与收到的摘要和长度匹配；要么是匹配的取消收到/观察，且有记录的取消请求，且无已已验收的产物。后者仅允许临时文件回收，从不进行制品导入或外部能力执行。
- 恰好是 `work/input.txt` 和 `work/output.txt`，两者均为受限制的常规文件，无符号链接或硬链接。未知条目会导致拒绝，而非递归删除。
- 由操作员批准的摘要，绑定那些确切的工作字节和证据。

```sh
an-agent-host work-reclaim HOST_STORE RUN_ID
## Inspect plan and approval_sha256 before approving it.
an-agent-host work-reclaim HOST_STORE RUN_ID --approve PLAN_SHA256
```

商店锁对元数据/清理操作进行序列化，而不是对子生命周期进行序列化。
正在进行的尝试没有有效的最终结算，无法被回收。在验证之后，
记录一个独占的`reclaim-intent.json`，两个文件和空目录被删除，并且`reclaim.json`记录了结果。部分删除或缺失的结果需要检查，而不是自动重试。不会移除陈旧的锁。
输入证据、已验收的产物、可执行文件、计划、收据、结算标记、诊断流和内核审计保持不变。现有的产物导入、检出和固定版本执行在回收后仍然有效。

没有结算标记的旧运行不被允许。失败和超时的运行会保留其工作成果，即使进程已被回收。未知的终止状态永远不会因经过的时间、退出声明或取消请求而被升级。未来政策可能会分别对这些情况加以资格认定；这里没有引入背景GC或保留调度器。

### 外部能力请求和批准

请求的套件将此有界JSON作为其已验收的输出：

```json
{
  "schema": "an-capability-request-v1",
  "capability": "artifact.read",
  "revision": "FULL_SHA256_REVISION"
}
```

未知字段、功能和无效版本将被拒绝。请求不能指定宿主路径、命令、凭证或延续可执行文件。操作员提供一个私有目录和已注册的延续发布：

```sh
an-agent-host capability-read HOST_STORE REQUEST_RUN_ID CATALOG RELEASE
## Inspect the catalog, requested revision, continuation release and limits.
an-agent-host capability-read HOST_STORE REQUEST_RUN_ID CATALOG RELEASE --approve PLAN_SHA256
```

预览会验证请求和现有的修订执行合同，而不会启动一个套件或给予其目录访问权限。批准仅针对该请求的证据、目录、修订、发布、后端和限制。宿主重新检查证据，记录一个独占的`capabilities/PLAN_SHA256/intent.json`，然后使用现有的受控修订执行器。延续接收到的选定字节作为其固定输入，绝不会使用目录路径或宿主凭证。结果将请求与延续接收关联起来。该接收会固定输入修订，并且正常的内核准入/审计路径仍然使用。

同一个授权不能被自动提交两次。在意图之后但结果之前发生中断，其状态是不确定的；即使套件实际上已经完成，也不会推断重试。执行错误会被保守地记录为不确定。在提交之前取消，不会创建授权；在执行过程中取消则会使用现有的监督者。这是一次新的有界运行，而不是请求过程的恢复。没有活跃的RPC服务器、递归请求调度器、HTTP能力、应用写服务或通用工作流引擎。

### 信任与限制

CLI/库调用方是受信任的宿主权威。审批摘要绑定一个已审核的计划；它不是认证令牌或秘密。不要将宿主存储、CLI 或审批功能直接暴露给不受信任的套件。操作系统沙箱强制执行，而非提示语，防止直接读取目录、网络访问、子进程和审计写入。存储和目录必须对受信任的宿主保持私有。静态链接检查无法防止恶意同用户重命名竞争。新增的记录保留现有的文件系统持久性语义，而非断电原子性或远程验证。

固定配置文件保留其原有的 8 KiB 输入、64 KiB 输出和五秒限制。内部工作副本不会被提升为修订版本。此示例仅证明 `artifact.read` 的中介边界；新的外部服务仍然需要其自身的受限授权和实际效果收据。

### 可执行接受

```sh
cargo test -p an-agent-host --test file_runtime
```

轻量级测试工具包通过注册、AgentControl准入和真实的原生沙箱执行。它生成一个产物，发出一个读取请求，拒绝直接访问目录，并将选定的字节传递给已批准的工具包。测试检查预览/错误批准/不支持的请求/取消以及不确定的重复提交是否不会启动延续。回收测试比较删除前后的保留字节，重新导入产品，拒绝修改后的批准、额外条目、链接、缺失结算和不匹配或未确认的观察结果。在真实silk仍在写入时，回收尝试在取消之前被拒绝；其部分输出仍然存在。并发的原生回归测试也会回收已确认取消的尝试，而不会影响其正在运行的对等体或保留的正式修订。这些测试仅删除隔离的测试拥有的工作副本。
