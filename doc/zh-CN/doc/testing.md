# 测试与跨仓库验证

[English](../../testing.md) · 中文译文，以英文为准。 · [中文目录](../README.md)

此合约指导测试放置和选择性迁移。它不会改变运行时行为，移动现有测试或替换当前CI命令。仓库验证仍定义在[AGENTS.md](../AGENTS.zh-CN.md)和工作流中。

## 所有权和语言

| 范围 | 所有者和首选实现 |
| --- | --- |
| 内部不变量、解析、身份检查、私有故障窗口 | Rust测试，位于拥有模块旁边或现有集成目标中 |
| 实际CLI组合、进程取消、文件系统托管和恢复 | 宿主验收；新黑盒套件首选Python，使用构建的二进制文件 |
| 编写、声明、冻结候选、打包和证据接收 | Loom测试；内部合约使用Rust，外部CLI组合使用Python |
| Loom发布由宿主加载并执行 | 狭窄配对验收，使用显式的Loom和宿主版本 |
| 浏览器或GUI集成 | 适配器拥有的测试；当适合现有浏览器工具时使用TS |
| 领域正确性 | Spool/示例拥有的测试，不使用宿主或Loom业务分支 |

语言是测试选择，而不是运行时依赖要求。在移动Rust测试时，如果没有测量到好处，应保留成熟的Rust测试。不要仅仅为了让外部测试触发内部故障窗口而暴露新的生产API。宿主压力和故障窗口矩阵应放在一个代理中；Loom应验证其交接合约，而无需重复完整的矩阵。现有覆盖率必须保留，直到展示出等效的替代方案。

## 放置和执行

保持私有Rust测试靠近其模块，在`cfg(test)`下，并将公共Rust套件放在拥有crate的`tests/`树中。未来的Python CLI套件应位于该crate的`tests/cli/`下，并带有本地README，列出前提条件、二进制参数、命令和支持的平台。这是一个放置规则，而不是声称这些套件已经迁移。

在显式的准备步骤中构建产品二进制文件，每个选定的修订版本、目标和构建配置执行一次。将它们的路径传递给外部测试；不要使用 `cargo run` 或在每个场景中重新构建工作区。一个旨在验证构建的测试仍然是一个显式的例外。Cargo 的 `test --no-run` 后跟 `test` 通常会重用测试二进制文件；这些并不本质上是两次完整的编译。

对于配对验收，记录两个源修订版本、二进制摘要、目标操作系统和架构，以及相关的配置文件/合约标识。历史套件可能固定不同的宿主修订版本；不要在它们之间静默地重用同一个二进制文件。缓存只是一个优化手段，绝不能作为输入匹配的证据。

每个外部运行器必须限制等待时间，保留失败输出，并仅清理它拥有的进程和文件。客户端超时并不表示执行终止。在终止未知时保留证据并拒绝破坏性清理；不要自动重试操作。在声称执行终止前应先进行实际执行，且应明确标记模拟的接收或故障。

## 迁移验收

对于每个选定的套件，记录旧的和新的入口点，并映射其断言和故障情况。在适用的情况下保留取消、过期结果拒绝、版本固定、终止确认和产物保留检查。保持所需的 CI 覆盖和支持平台检查；不可用的前提条件不是通过验收的结果。在相同审查更改中，与 CI 和下游调用者协调任何入口点替换。

运行两个版本以进行迁移比较，然后在等价性确立后才移除重复的覆盖。不要削弱门控、提高截止时间或隐藏竞争以获得更快的结果。标准 Cargo 检查仍然是必需的；单独运行受影响的外部套件，并报告跳过的实际验收。

分别测量依赖项/产品编译、测试编译/链接和执行，如果工具链允许的话。记录运行器/平台、版本、工具链、缓存状态和重复测量；区分冷启动和热启动。Python 可以移除 Rust 测试编译，但不能移除产品编译。不要根据单次组合 CI 持续时间或更改运行器来声称性能提升。


## CI 依赖项缓存

宿主 CI 通过 rustup 安装仓库中指定的 `rust-toolchain.toml` 工具链，包括其声明的组件。不要在选择固定版本之前安装单独的移动 `stable` 版本。临时托管运行器将该版本设为默认（包括调用 rustc 的固定装置），并且仅为此作业移除其他安装的工具链。缓存操作会指纹所有安装的编译器；否则未使用的预安装稳定版本差异可能会使缓存失效，即使源代码相同。此工作流程不会更改开发人员的机器。

固定的 [rust-cache 动作](https://github.com/Swatinem/rust-cache) 覆盖了 `. -> target` 和 `tools/archcheck -> target` 的一次缓存操作。这些仍然保持为独立的 Cargo 工作区和构建目录。该动作通过编译器和 Cargo 配置/锁定文件来指纹依赖项；我们额外的键则区分运行器操作系统和架构。`host-deps-v1` 前缀提供了显式的缓存命名空间。默认的仅依赖项缓存保持项目编译和所有检查处于活动状态；缓存的二进制文件永远不会被视为通过验收的证据。该动作禁用了 Cargo 的增量编译，以适应此 CI 缓存策略。

注册表/ Git 依赖项和依赖项构建输出被缓存，而不是生命周期收据、工作区产品、凭证或测试结果。已安装的 Cargo 二进制文件被排除。缓存恢复不能跳过格式化、编译、工作区测试、Clippy、架构工具测试/检查或架构门控。现有的作业名称、操作系统矩阵、超时和证据上传保持不变。GitHub 的正常缓存范围适用；PR 缓存不是新的运行时信任授权。

为了测量缓存的变化，首先在全新的命名空间中运行PR，并确认其缓存日志中出现未命中。在该运行成功并保存缓存之后，再次运行相同的提交，并记录精确命中的观察结果。比较每个操作系统下的作业和步骤的持续时间，包括缓存恢复/保存，而不仅仅是编译过程。一次完成的CI重新运行是一次全新的测试运行，而不是对未知产品操作的重试。不要刷新无关的缓存或增加超时时间以改善比较。在PR中保留运行/尝试链接，并区分运行器差异与已建立的改进。缓存未命中仍然完全支持，并且必须通过相同的检查点。

对于跨仓库的接受，为每个资格作业所选择的宿主检出缓存，并在该作业的标识下保留其固定的版本。不同的历史宿主发布版本即使暴露相似的CLI命令，也是不同的构建输入。不要在这些作业之间共享同一个宿主可执行文件以节省时间。一个组合的依赖缓存可能覆盖多个目标目录，但绝不要缓存已接受的产品，也不要用缓存命中替代接收验证。

## 单主 agent 基准 v1

场景清单已接入原有守护服务验收入口。每轮冻结输入、源码清单、程序摘要和环境，证据由分支管理。Krita 文档绑定保存场景仍有明确能力缺口。[场景清单](../../../crates/an-agent-host/tests/benchmarks/single_agent_v1.json)

### 基线与范围

一项完整任务使用一个主 agent 会话，跨 spool 阶段继续使用同一会话，逐步加载描述、契约和所需知识。外部 harness 承担模型循环，宿主承担调度、任务授权、生命周期、活动记录和产物验收。补充指令与重连必须保留原任务身份。出现隐藏的模型子任务时，该次运行失去单主 agent 基线资格。

允许主 agent 并发调用确定性程序、等待后台工具并继续处理结果。记录每个程序与模型会话，固定 harness 暴露的工具和委派能力。所有参与任务的模型调用都计入用量。多个独立用户会话的并发单独评测。

### 六组指标

| 指标 | 计算口径 |
| --- | --- |
| 验收交付率 | 通过独立领域检查、宿主验收和所需资源释放检查的正向任务次数，除以已开始的正向任务次数。同时记录每次重复都成功的 case 比例。 |
| 每次合格交付成本 | 同一场景族所有正向运行的用量总和，包括失败与修复，除以合格交付数。另列每次运行和控制类场景的消耗。 |
| 端到端时延 | 从宿主接收任务到合格交付或预期控制结果。记录排队、发现、模型调用、程序执行、人工等待与验收时间，以及重叠区间。 |
| 人工介入 | 每项任务额外纠正、手工救援的次数和实际操作时间。预先约定的授权与固定澄清另计。 |
| 控制完整性 | 越权效果、错误版本验收、不确定操作重放、提前回收的次数，以及预期拒绝、取消和恢复的成功率。 |
| 发现与上下文效率 | 首次合格选择率、最终有效选择率、首次正确行动耗时、发现调用数、实际加载及重复加载的字节数、可观测 token 用量。 |

正向任务包含直接交付和澄清后交付。预期拒绝、取消、保留未知状态、能力缺失各有自己的分母。超时和失败修复计入正向任务失败。零交付时，每次交付成本为未定义，同时展示已经消耗的总量。报告已开始、受阻、无效和完成的数量。

以独立检查验证文件和应用状态，通过活动记录定位原因。这一结果验收方法参考现有 agent 评测实践。[Anthropic 评测指南](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

同时报告单次成功率和每次重复均成功的 case 比例，以观察稳定性。重复成功指标参考 tau-bench 的可靠性评估思路。[Tau-bench 论文](https://arxiv.org/abs/2406.12045)

保留提供方原始 token 计数及语义。缓存输入若已包含在输入总量中，只计一次，推理 token 与输出总量也采用相同规则。按执行、turn 和 attempt 身份去重累计用量快照，覆盖失败、补充指令、上下文压缩和修复。缺失值记为 `null` 并报告覆盖率。金额换算需要对应的价格版本与计费方式。

有观测数据时记录模型调用耗时。模型内部推理耗时可能未知，不能用总耗时减去程序耗时推算。分别记录机器活动时间、用户等待时间、预期人工等待、应用启动和工具执行。无法控制的提供方缓存记为未知。成功、失败和截止时间截断的运行分别统计时延。

发现评分接受满足同一契约的等价 spool，也允许合理澄清。额外知识加载、错误版本指令与最终交付分别记录。字节数描述披露体积，token 估算需标注 tokenizer 和版本，实际计费用量使用提供方数据。

### 场景矩阵与初始规模

建议八组、每组三个 case。先各取第一个 case 跑一次，共八次，检查采集与验收。首轮完整基线对全部 24 个 case 各重复三次，共 72 次。该规模属于初始规划，可根据试跑成本调整。先看每个 case 和场景族的结果。三次重复用于诊断和描述性稳定性检查，尾延迟与架构优越性结论需要另行设计样本量并报告不确定性。

| 场景族 | 三个 case | 主要观察 |
| --- | --- | --- |
| 文档交付 | 精确 PDF 表格、修订与换行、固定澄清 | Markdown 与可编辑 Excel 的数值、公式、版本和保管 |
| Spool 选择 | 4、16、64 个含相近描述的候选 | 选择正确性与发现成本 |
| 上下文压力 | 同一任务附带 0、16、64 KiB 无关知识 | 按需加载、约束保持与过时知识处理 |
| 后台控制 | 补充指令、守护服务重连、取消 | 原任务身份、最新指令与资源释放 |
| 工作结构 | 独立程序、独立推理材料、依赖步骤 | 程序并发与推理关键路径 |
| 边界故障 | 越权输入、过期发布、效果回执丢失 | 拒绝、来源与不确定状态保留 |
| 机械交付 | 蒸汽机全链、四缸复用、Krita 目标错位 | 领域质量、可编辑产物和文档绑定 |
| 新能力 | 陌生 spool 标识、输入结构变化、缺失能力 | 根据契约迁移和明确报告不支持 |

文档输入采用合成数据并固定预期行和公式。首个表格合计 EUR 38.50，修改数量的版本合计 EUR 39.00。含糊输入与固定澄清回答一同冻结。机械场景复用 an-spool 的领域检查，在运行前固定分辨率、帧数、应用版本、图层要求与视觉容差。需要人工判断的视觉标准单列结果。

首轮上下文扫描测量无关材料增加的影响。若要研究上下文窗口饱和，再加入必要知识逐渐增多的独立扫描。首轮披露对比保持任务必需信息和难度一致。

### 输入冻结与运行证据

评分前固定源码版本、可执行文件、spool 发布、输入、判定规则、候选顺序、模型和 harness 设置、授权、截止时间与 token 预算。场景配方记录输入和判定规则摘要后才具备执行条件。故障触发绑定可观察事件，复用已有测试入口或控制端 fixture。预期答案保存在 agent 无权访问的位置，任务要求本身应完整告知 agent。

先通过不评分的试跑校准预算与超时，再对所有比较方案采用同一配置。各次运行使用新的任务状态，交错执行顺序，记录机器并发、应用启动状态和缓存观察。超时操作在结算前保留原身份，后续独立试验需要已释放资源或独立隔离的资源。

调优描述和提示前预留未见过的输入变化，分别报告开发集和保留集。平台无法执行的必要场景记为受阻并展示覆盖缺口。存在受阻场景时，整套验收为部分完成。控制器或判定规则错误会使受影响的比较无效，需要留下修正记录。

每次记录 case 与重复编号、会话及操作身份、观察到的效果、产物摘要、判定结果、指令及授权版本、披露事件、分阶段时间、用量、人工介入、释放证据与未知状态。保存提供方实际开放的事件，私有推理内容保持未知。验收摘要沿用分支证据流程。

### 复用入口与采集缺口

文档验收使用同一 Codex thread 的两轮交互，固定澄清场景增加一轮。主 agent 读取绑定版本的知识及宿主已验收的 Markdown，应用库负责 PDF 提取和工作簿生成。独立检查 Markdown 与 OOXML 的行值、公式，宿主继续负责发布、验收和撤销。[文档验收](../../../crates/an-agent-host/tests/cli/document_activity.py)

HarnessAdapter 验收使用两个 owner 的确定性协议 fixture，可复用身份、补充指令、游标和取消断言。真实提供方基准需要在单主任务上获得相同的可观测结果。[HarnessAdapter 验收](../../../crates/an-agent-host/tests/cli/native_harness_adapter.py)

权限拒绝和撤销复用现有检查，并与真实任务的效果关联。机械链固定 an-spool 领域验收版本。宿主拥有调度测量与通用不变量，spool 测试拥有领域正确性。[权限验收](../../../crates/an-agent-host/tests/cli/native_task_permissions.py)

`activity.harness.metrics` 读取原始提供方事件和授权工具回执，去重会话累计 token 并检查计数倒退。UTF-8 读取记录内容摘要、字节数及宿主处理耗时，知识分类使用冻结摘要。模型实际消费程度和内部推理耗时保留为未知。

`single_agent_benchmark.py` 先运行 `--phase smoke`，再运行 `--phase full`。传入 `--host`、`--codex`、`--evidence`、`--archive`、`--spool`、`--shuttle`、`--mechanical-fixtures` 与 `--mechanical-site`。macOS 本地套接字要求较短的证据路径，归档放在分支忽略的目录中。控制端需要 pypdf、XlsxWriter 与选定的机械运行库。宿主执行时间上限，token 阈值在运行后核对，失败用量保留。

回执丢失场景目前验证补充指令确认丢失后的未知状态与去重。应用保存效果另行验收。当前 Krita 桥接按规范文件路径定位，单独切换焦点不足以构成目标错位，绑定宿主授权的保存接口仍缺失，每次重复均记录阻塞。机械检查覆盖几何、运动、视频尺寸和帧数、可编辑 Blender 文件及 ORA 首帧参考，视觉风格与 Krita GUI 回存单独说明。

### 何时考虑其它架构

先在同一主 agent、工具、模型、授权和输入上比较按需披露与全量加载。评估精简描述、知识索引和确定性程序并发是否能解决问题。将工具故障、知识缺失、资源竞争与 agent 拓扑分别归因。

在不同冻结输入中重复出现的弱点，可触发一次有边界的架构对比实验。记录问题假设和受影响场景族，根据独立推理工作或上下文相互干扰等实际原因选择候选。在开发集与保留集上配对比较，并使用相同质量验收。

获得基线后，预先约定允许的质量变化、要求的成本或时延收益和比较预算。既比较相同预算下的质量，也比较同等质量下的成本和耗时，汇总主 agent 与所有 worker 的用量。变更模型、工具和授权的试验另行标识。

采用其它架构需要超出运行波动的收益、相关采集完整、零观测控制违规，并核算增加的维护成本、依赖和恢复路径。渲染环节耗时高，本身不足以支持增加模型 agent。单主 agent 保持默认，直到证据支持具体调整。
