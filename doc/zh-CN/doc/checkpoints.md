## 实例状态提交

一个发布包含不可变的领域代码和知识。一个实例固定该发布并拥有一个已提交的状态修订版本。每次执行尝试都从一个全新的工作目录开始。Spool 定义状态转换；宿主管理身份、授权、证据和发布，而不解释业务规则。后端进程或虚拟机的状态不是权威的实例状态。

这个有限的原生配置文件重用了构件修订版本，`run_revision`，内核准入，文件工具隔离和已确定运行验证。它不添加执行器、核心抽象或 Loom 依赖。

本文档描述了原始的仅捆绑配置文件。选择加入的[检查点清单配置文件](checkpoints.md)将交付产品存储与状态分离，添加了冻结接收者和已提交的消费证据。选择加入后，后续提交必须提供清单；旧版提交命令不能静默丢弃交付或保留元数据。

### 捆绑和命令

该工具使用此 JSON 包装器读取 `input.txt` 并写入 `output.txt`：

```json
{"schema":"an-instance-bundle-v1","state":"0","product":"","report":""}
```

所有三个负载都是不透明的 UTF-8 字符串。未知的信封字段和模式将被拒绝；业务正确性仍由 spool 负责。整个之前的捆绑包是下一个输入，包括其产品和报告。此切片不会添加第二个实时输入通道或上下文组装器。序列化的捆绑包必须符合现有的 8192 字节执行输入限制。过大输出可以继续作为接受的运行产物，但不能成为下一个状态。

```text
an-agent-host instance-init STORE INSTANCE RELEASE STATE_FILE
an-agent-host instance-init STORE INSTANCE RELEASE STATE_FILE --approve DIGEST
an-agent-host instance-show STORE INSTANCE [REVISION]
an-agent-host instance-run STORE INSTANCE REVISION
an-agent-host instance-run STORE INSTANCE REVISION --execute
an-agent-host instance-commit STORE INSTANCE EXPECTED RUN_ID
an-agent-host instance-commit STORE INSTANCE EXPECTED RUN_ID --approve DIGEST
```

`INSTANCE` 是一个规范的 UUID；发布和修订标识符是完整的哈希值。
初始化和提交首先返回一个计划和批准摘要。执行和
发布是分开的授权。摘要绑定一个已审查的计划；它们
不是凭证。只有受信任的宿主才可以批准、访问私有存储或
发布状态。套件不能通过生成摘要来自我授权。

两次运行可能会消耗相同的已提交修订。在第一次提交推进头之后，
第二次运行将返回 `conflict` 并且 CLI 以失败退出，即使
两者生成了相同的字节状态。一个已批准的过时提交记录了预期
和实际的修订。没有自动重试、变基或覆盖。该
存储锁仍然对头验证和提交进行串行化。独立的尝试可以
在单独的运行目录中并发执行；这不是一个新的调度器。

### 发布和中断

宿主在 `STORE/instances/INSTANCE` 下存储实例元数据、私有修订目录、`HEAD` 和提交日志。初始化准备一个待处理
目录并将其重命名为实际位置。现有的实例和中断的待处理
初始化永远不会被覆盖。

一个提交验证已确认的成功终止、密封的运行证据、
固定的发布和精确的输入修订绑定。在存储锁下，它检查
预期的头、写入一个独占意图、存储完整的候选
包，并原子地将一个准备好的指针覆盖到 `HEAD`。该指针更改
发布状态、产品和报告。一个结果记录随后跟随。

一个被接受的运行输出仍然是一个候选，直到此发布。读者可能
只能选择头或其已验证的祖先，而不是暂存或孤儿修订。历史遍历
限制为 1024 个修订，超过该限制则失败关闭。私有目录
不得作为已发布产品的列表进行宣传。一个受信任的调用者可以从已提交的包中导出产品；此切片
不会自动添加下游订阅。

在指针替换之前发生中断会导致旧的捆绑包仍然可见。在指针替换之后发生中断可能导致已提交的修订版本缺少结果记录。在决定发生了什么之前，请检查 `HEAD` 及其运行/审批来源；独占意图防止盲目重新提交。这是进程可见的原子发布，而不是断电持久性的保证，也不是分布式比较并交换，或对外部影响的回滚。私有存储假设宿主是可信的，并且不能防止具有相同文件系统权限的恶意进程。

### 接受

```sh
cargo test -p an-agent-host --test file_runtime instance::
```

测试用例编译并注册了一个真实的命令行计数器工具包。十进制解析和递增规则仅存在于该工具包中。原生隔离机制拒绝直接访问宿主状态、输入修改、在工作区外写入以及子进程执行。接受序列如下：

1. 初始化状态为 0，并从该版本执行两次不同的运行。
2. 批准第一个结果，发布状态 1，以及其产品和报告。
3. 拒绝第二个结果，因其为过时数据，且不更改已提交的包。
4. 通过现有的已批准清理路径回收两个旧的工作目录。
5. 在新目录中启动一个全新的宿主 CLI 和工具包进程，消费状态 1，并发布状态 2，同时较旧的已提交版本仍可读。

负向检查覆盖了外来实例候选、缺失结算证据、中断的提交意图、格式错误的领域输入、无效的信封、孤立的修订版本和损坏的存储内容。这展示了从已提交数据在全新的原生进程和目录中继续执行。它不声称虚拟机重建、内存恢复、任意应用恢复或状态迁移。

## 检查点、提交清单和交付证据

### 合约

一个 spool 发布定义了领域状态、转换和验证。一个检查点记录了已提交的状态以及继续该状态所需的固定数据引用。宿主拥有发布、交付证据和保留权；后端的工作磁盘或内存快照不是状态的权威。磁带解释了执行过程，但不会替代这些记录。

有界文件工具包配置文件在可执行边界处保留现有的状态/产品/报告信封。一个检查点提交会将产品提取到一个单独的制品修订版本中，清除存储状态信封中的产品字段，并在不可变检查点的来源中包含一个提交清单。更新实例头会同时发布状态、产品引用、冻结的收件人列表和累积消费证据。仅阶段化操作不会发布任何内容。

操作员审核的清单声明了`recipients`（实例UUID），`state_refs`（发布者实例和已提交检查点对），以及`retention`（`keep`或`delivery`）。这些声明并不授权文件系统访问权限。宿主验证身份和引用；套件仍然定义领域语义。该配置文件每次提交处理一个UTF-8产品，最多支持32个接收者/引用和每个实例128个已消费事件。超过限制将显式失败。

### 交付与中断

一个事件通过其发布者和不可变检查点修订版本来标识。其产品和接收者集合永远不会跟随可变的最新指针。下游执行输入包含其当前状态和现有`product`字段中的事件产品。由宿主生成的输入修订版本将事件、接收者和预期的下游状态绑定在一起。成功的套件输出仅是一个候选项。

下游检查点提交验证这种绑定，并记录消费情况及其新状态。单独的确认文件是可重建的收据，而不是业务处理是否发生的权威依据。如果确认文件丢失，交付将找到已提交的消费情况并恢复收据，而无需运行套件。不提供通用的“恰好一次”外部副作用保证。

在交付执行之前，宿主记录一个独占尝试意图。未被消费的尝试永远不会自动重新启动，包括在崩溃后。操作员可以检查已结算的候选项并显式提交。缺少或未确认的结算无法提交。在检查点发布后发生中断的情况下，即使最终提交结果或确认文件缺失，也可以从已提交的历史记录中进行协调。具有未知结果的外部影响需要其自身的协调；此配置文件不会引发外部影响。

现有的单存储锁保护发布和回收操作。此切片不实现分布式写入器、活锁、虚拟机恢复或断电事务。过期锁和中断意图需要操作员检查。

### 保留

每个清单都会明确声明保留策略；标准示例使用`keep`。
显式批准回收`delivery`产品需要每个冻结接收者都已提交消费，并且没有保留的检查点通过`state_refs`引用它。所有已提交的检查点历史记录都保留在这个切片中，因此历史引用也会固定数据。故意没有隐式的歷史清理或引用过期机制。

回收仅删除独立的交付产品内容。其修订清单和一个墓碑记录仍然存在。执行证据和原始接受运行输出按照现有策略保留；回收不是对所有副本的彻底安全擦除。实例状态和报告仍然可以检查和运行。未发布的预发布内容不会自动收集。现有的已结算工作副本清理仍然独立，并且仍然需要确认终止。

扫描限制为256个实例和每个实例1024个修订；格式错误、未识别或过多的条目将导致扫描失败关闭。没有引入后台垃圾回收器、订阅服务或领域工作流引擎。

### CLI 和验收测试

清单是一个有界的 JSON 文件，例如：

```json
{
  "schema": "an-checkpoint-manifest-v1",
  "recipients": [],
  "state_refs": [],
  "retention": "keep"
}
```

接收者初始化为实例 UUID。每个状态引用都有 `instance`
和 `revision` 字段，用于标识发布者的已提交检查点。状态引用必须完全由 spool/操作者声明；宿主无法发现任意域数据内部的依赖关系。批准将声明的恢复根绑定，但不会自动将引用文件挂载到 kit 中。此切片验证其可用性并保护保留；更丰富的状态依赖关系材料化被延迟。批准还将清单与确切的候选和预期状态绑定。该文件是数据，而不是授权脚本。现有的 `instance-init`、`instance-run` 和 `instance-show`
仍然是初始化、普通执行和检查的入口点。

```text
an-agent-host checkpoint-commit STORE INSTANCE EXPECTED RUN MANIFEST [--approve DIGEST]
an-agent-host checkpoint-deliver STORE PUBLISHER REVISION RECIPIENT [--execute]
an-agent-host product-reclaim STORE PUBLISHER REVISION [--approve DIGEST]
```

执行需要受信任操作员的显式`--execute`；提交和回收首先生成一个批准摘要。在一次交付运行之后，通过`checkpoint-commit`提交其已结算的候选内容。再次调用`checkpoint-deliver`以协调确认；这不会执行已被消费的事件。缺少确认本身不会阻止回收，当已提交消费可用时。一旦使用了检查点清单，旧版`instance-commit`将拒绝删除其元数据。

```sh
cargo test -p an-agent-host --test file_runtime checkpoint::
```

注册的本地 fixture 产生 `count=5`；两个独立实例将其添加到各自的域状态中，分别产生 15 和 25。算术和输入解释完全在 kit 中进行。测试覆盖以下内容：

- 缺少结算将拒绝提交，并保持之前的检查点不变。
- 阶段与头发布之间的故障会留下一个不可见的孤儿。之前的狀態可以用于显式授权的新运行；孤儿无法交付事件或成为回收目标。
- 头发布之后的文件系统故障会使 CLI 失败；新的 CLI 调用会重新协调已提交的消费，而不是重新执行 kit。
- 删除确认文件不会改变消费或创建新的运行。
- 未消费的尝试会被隐式重新执行所阻止。
- 两个消费者都可以在不保留状态引用的情况下完成，允许显式产品回收；上游会从不包含旧产品的状态继续。
- 保留的状态引用即使在两个确认都完成以及当前状态放弃引用后，仍会阻止回收，因为历史检查点仍然被保留。`keep` 产品会独立地保持保护。

注入的发布失败模拟了中断的结果/确认路径；它不是断电耐久性测试或虚拟机检查点实验。临时执行副本和原始证据保留其现有的、单独文档化的清理策略。

### 中断的产品回收

回收操作在删除产品字节之前会写入意图。后续的调用首先会检查保留的意图是否与已提交的产品引用和哈希修订清单相匹配，然后再尝试读取现在可能已经不存在的内容。这是一个只读的协调路径，而不是删除重试。一个完整的匹配收据且内容缺失则报告成功；缺失、部分缺失或无法读取的收据则报告`uncertain`，并指出观察到的内容存在情况以及需要操作员进行协调操作。
矛盾的身份或成功收据但内容仍然存在则关闭失败。
结果写入失败会明确报告删除可能已经发生。
状态、清单和原始证据仍然保留。不会自动进行收据修复、复活或重试。测试会模拟删除后的真实收据创建失败以及在部分写入和同步确认周围的保留崩溃状态；它们不声称断电持久性，也不证明缺失字节消失的原因。
