## 术语表

| --- | --- | --- |
| 会话 | 一个具有连续性的交互时间段，例如核心代理的私有磁带和文件 | 一个**cohort**（群体）在同一个准入和取消政策下执行有限的工作 |
| 线程 | 一个执行线程，或在明确标识时作为对话线程 | 一个cohort成员是一个**dispatch**（调度）。`AgentControl::open_agent`通过卡ID打开一个挂载的**代理** |
| 上下文 | 为接收者选择的材料 | 一个**交付绑定**或**阶段绑定**标识一个协议操作。传输的文本是一个**上下文数据包** |
| 工作区 | 参与者使用材料和版本的环境 | 核心**工作区账本**（`WorkspaceLedger`）记录事实和预测。工作区对象存储拥有版本化的树和文件 |

一个cohort可以跨越spool实例。调度成员控制工作。一个对等体授权将披露绑定到一个精确的spool激活。一个工作者或对话句柄不会授予这种授权。核心会话和工作区对象存储保留其原有的名称。

## 所有权和身份

| 概念 | 含义 | 不等同于 |
| --- | --- | --- |
| 工作区 | 宿主控制的版本化材料和事实命名空间 | 一个对等体邮箱或共享模型对话 |
| spool激活 | 与原生端点绑定的实例、释放和轮次控制生成 | 一个模型对话、一个授权或一个新的隔离边界 |
| 操作系统线程/进程 | 后端执行机制 | 一个上下文身份或一个领域工作流节点 |
| spool实例 | 与释放绑定的领域身份，具有显式提交状态 | 一个对话或模型会话 |
| 尝试 | 一个精确的准入执行，选定的输入/状态和结算证据 | 持久化会话或一个可自动恢复的任务 |
| 艺术品引用 | 精确管理的版本和声明保留字节的原因 | 一个可变路径、隐式最新版本或执行权限 |

使用实例激活来进行对等地址。暂停和恢复操作会推进生成并设置旧的授权。本地的[cohort adapter](../../../crates/an-agent-host/src/native_spool/events/cohorts.rs)将有限的分发跨实例进行分组。关闭该组会检查其结算情况。它会将激活、私有对话带和独立持有的产物引用留在各自的所有者处。每个尝试都保留自己的隔离、临时存储和固定输入/状态身份。

宿主工作者和操作系统线程可能随时间执行不同的操作。将模型上下文绑定到授权参与者、选定的材料和 harness 处理句柄，而不是工作者/TID 或整个工作区。在一个共享 spool 环境中的私有上下文并不是独立的安全边界。现有的 harness 保留自己的历史记录；撤销文件访问不会擦除之前的披露。

宿主拥有有效的授权、身份、取消、引用保管和边界证据。spool 拥有领域状态充足性、内部序列化和有用摘要内容。Loom 描述了预期的接口、保留需求和上下文合同，进行验证和打包；它不会授予访问权限、运行调度器或收集运行时文件。现有的 harness 拥有自己的本地对话历史和压缩。Weaver 保持为一个可替换的开发助手，而不是第二个运行时监督者。

## 通信和上下文边界

工作区事实描述了接受的材料变化。地址、请求/回复、订阅授权和交付确认属于宿主协议边界。文件可能携带协议信封或不可变的引用负载；任意共享目录写入不能成为隐式命令。接收消息、完成执行和接受输出是不同的事件。因果下游工作不会继承上游取消所有权。保留现有事件/订阅交付身份和无重放边界。

材料的读取权限并不意味着可以向模型服务披露该材料。
域代码/ harnesses 会选择有用的上下文；宿主会检查访问权限、接收者、版本和有效权限。核心工作区 `env` 保持受信任的宿主配置，而不是接收者消息、检索文本或任意文件的接收端：它进入系统信封。上下文数据包保持为未受信任的数据；它们的哈希值和受众字段不能独立授权披露。

### 有限的对等上下文

对于显式的交接，使用 `spool-peer request` 并配合请求模式 `an-native-peer-context-request-v1`。使用与普通产物请求相同的字段。选择一个正式接受的文本输出，包含完整的 `an-context-v1` 数据包。其受众是接收方的 spool 实例 UUID。包含的对等授权绑定两个激活、生成、确切的产物版本和摘要、序列化大小和请求名称。请求发布和接收方执行需要分别授权。普通产物请求和回复输出保持其原有行为。

宿主在发布前和阶段准入前验证数据包摘要、实际受众和最多 4096 字节的序列化数据。接收方将选定的数据包作为普通的未受信任输入读取。作者可以选择一个简短的输出或摘录，并将完整的源文件单独保存。过大、缺失、格式错误或被修改的数据包将被拒绝。此路径使用现有的 legacy-catalog 对等读取器。注册复制的对等读取仍需要其自身的托管支持。不需要工作区事实、核心磁带或模型调用。向接收方内部的模型或私有参与者披露需要单独的权限。

接收阶段成功并确认终止后，操作员可以运行`spool-peer deliver-agent SOURCE REQUEST AGENT_UUID`。接收释放必须包含`silk/agents.json`，即一个包含一到八张不同无工具v1核心代理卡的JSON数组（总计32 KiB）。预览绑定确切的请求、接收生成、运行、输入摘要和所选卡。批准其摘要以开启一个全新的本地AgentControl会话。只有该代理会收到一个不可信的剪辑。收据标识该剪辑及其私有数据包文件。新的数据包保留确切的文本，将代理命名为观众，并引用交接批准作为其来源。两种序列化格式都必须符合线路上的限制。

一个专用接收方拥有的交接目录在导入前对请求进行 fencing（限制）。如果完成证据丢失，应保留该目录以供检查。另一份交付需要一个新的对等请求。撤销或激活轮换会关闭准入；它不能撤回已经交付的内容。现有的 `model PROFILE PACKET OUTPUT` 命令预览了所选字节的单独披露。检查收据并批准该命令的摘要以发送一个请求。模型参与在操作员的配置文件下重新开始。不继承任何提供者凭证或对话。此资格覆盖宿主指导的交付；共享执行环境的参与者之间没有新的安全边界。


### 本地读取的释放上限

请求者可以导出一个不可变的`silk/peer-read.json`声明。其`an-native-peer-read-v1`作用域选择一个任务、确切的工作者释放摘要、接受的文本输出槽位、工作者回复槽位以及文本/时间上限。在现有的有界上下文请求中提供`read: {task, material_revision}`。修订选择请求实例的确切接受输出。在此路由中，声明和请求字段都是必需的。本地读取不包含检查点槽位或向模型披露的请求。

在范围内，预览返回 `needs_authorization` 并使用现有的宿主批准摘要。为精确的计划提供先前授权的摘要可接受请求。该计划绑定两个激活项，即材料和接收者，以及上限。在范围外，宿主在创建对等记录之前拒绝请求。工作者仍然使用普通的监督执行边界。其接受的固定回复可以由主代理在不执行响应阶段的情况下进行检查。一个作用域请求会保留在其选定的 spool 工作者处，不能转交给内部代理卡。只有这个本地路由是合格的。

## 运行时接受矩阵

| 设计需求 | 当前证据 | 剩余差距 |
| --- | --- | --- |
| 固定授权的产物交付 | `native_events.py`, `native_data_state.py`, `native_peer.py` | 缺少通用的实时 IPC 端点 |
| 不进行隐式私有笔记交付 | `native_material_boundary.py`: 实际读/写拒绝，事实日志未更改，无交付，仅声明输出 | 未测试模型摄入；这是一个前台适配器，不是自动监视器 |
| 私有内容仍保留在其他尝试之外 | 同一套检查另一个实例的输出/身份和工作区日志 | 本地策略允许文件元数据；它不会隐藏存在性或提供恶意代码隔离 |
| 取消一个所有者而不取消另一个 | `native_sessions.py`: 重叠的实际执行 | 客户端丢失后由 `routed_supervision.py` 验证；缺少所有者收据会使尝试保持挂起 |
| 未知执行无法释放材料 | `native_data_state.py`, 损失收据的队列案例 | 缺失的收据在执行后被注入；任意崩溃恢复未被证明 |
| 旧交付无法成为新实例的工作 | `native_route_successor.py`; `native_peer.py` 在暂停/恢复后拒绝过时回复 | 对等端点使用实例身份和轮次生成，而不是单独的会话管理器 |
| 等待 A 离开后 B 仍能执行 | `native_peer.py`: B 在 A 有独立活跃工作时运行；等待没有进程或挂起的执行锁 | 缺少通用的阻塞 IPC 等待者，公平性保证或全局调度器 |

第一次本地材料运行拒绝了所有三个受保护内容的读/写，但暴露了所有三个路径的元数据。请保持这个限制明确，而不是削弱断言或将协议身份检查呈现为信息流隔离。原始机器路径和命令证据仍保留在本地。

## 分阶段对等交换

对于经过审查的无头对 A 和 B，受信任的宿主将接受的 A 输出转换为对一个精确的 B 端点的请求。A 已完成其计算；等待是请求实例下的宿主拥有的记录，而不是空闲的 OS 线程、活跃模型、工作区事件或扫描目录的权限。请求模式是 `an-native-peer-request-v1`；指定 `source_run`、
`source_output`、`target`、`reply_output`，以及 `wall_seconds`（1–300）。可选的 `request_state` 和 `response_state` 是各自接收方声明状态输入的确切版本，绝非隐式的 HEAD。本地生成是现有的 `(instance, release, round-control generation)` 绑定。重新加载具有不同的实例标识；暂停/恢复会改变轮次生成。

```text
spool-peer request A NAME SPEC.json        # preview; approve its exact digest
spool-peer show A NAME                    # observation only
spool-peer run A NAME request             # separately approve B's exact start
spool-accept B B_RUN                      # formally accept B's declared output
spool-peer reply A NAME                   # separately approve the correlated reply
spool-peer run A NAME response            # separately approve A's continuation
spool-accept A A_RUN                      # accept the final product independently
spool-peer cancel A NAME                  # revoke future peer admission; no signal
```

每次变更在预览后都会花费 `--approve HASH`。每个阶段都有一个源自已批准请求和阶段的本机尝试身份。持久阶段意图在执行之前。已经承认或不确定的阶段拒绝重放；不会发生隐式的转发或下一次运行。回复必须同时匹配两端点、原始请求、验证的目标终止、已验收的输出和精确的产物版本。观察可以区分不确定、撤销、过时和就绪状态；它从不授权执行或收集。

撤销栅栏阻止未来的准入和消费；已经准入的工作可以完成并继续由其原始进程监督者拥有。回收需要原始终止的证据。没有后台工作者或实时套接字服务，没有代码代理对这个操作符CLI的访问，也没有工作区记录。请求名称是一次性使用（每个请求者64个）。每个准入的本机阶段都会固定其输入。成功的对等固定当前会保留：事件确认不能释放它们。等待本身并不是永久保留的保证；退休或不可用的材料拒绝新的执行。没有正式的负载垃圾回收机制启用。

## 产物生命周期：仅在有明确原因时保留字节

请将以下三个概念区分开：

- **证据引用：** 身份、摘要、来源、结果和因果联系。它在负载收集后仍然存在，但不保证字节仍然可用。
- **保留固定：** 注册的所有者仍然需要确切的字节。示例包括：已准入的尝试、未解决的交付、明确选择的检查点依赖项，或操作符保留决策。
- **独立副本：** 一个经过验证的检出/快照，具有独立的保管。它可以比原始对象存在更久，但不能证明其所有者已释放原始对象。

内容摘要不是保留固定或发布者认证。不要扫描不透明状态或代理文本来猜测依赖项。声明在Spool中的状态引用必须明确与检查点提交；旧检查点会保留其固定，直到明确退休。复制到独立保留检查点中的状态不需要仅仅因为来源提及它而固定其来源。

提议的有界序列：

1. 通过现有的结算和托管门接受不可变的输出。
2. 在托管消费者依赖该版本之前，获取一个持久的 pin。
   绑定 catalog/revision/digest，拥有实例和尝试/检查点身份，
   生成和用途。注册和准入必须具有一个顺序，以防止集合发生竞争。在 pin 和运行意图之间发生崩溃可能会泄露一个 pin；
   它绝不能允许删除正在使用的输入。
3. 使用现有的单调退休操作关闭新输入的准入。
4. 在其所有者不再需要字节后，显式释放每个符合条件的 pin。
   仅进程退出、确认、队列关闭、经过时间或缺失心跳无法释放它。未知的执行/交付状态仍会保持 pin。
5. 仅在声明为关闭的托管作用域中预览和批准集合，且没有剩余的 pin。
   在记录删除意图之前，必须在原始托管边界下重新验证关闭状态、pin、所有权和精确的库存。
6. 保留不可变的元数据、收据和内容不可用的墓碑标记。
   内容读取必须报告已收集/不可用，绝不能假装成功。
   未知的删除仍会被隔离以供检查，不进行自动重试。

这是目标协议，而不是现有托管之外的第二个实现。
在假设成立的情况下，重用现有的集合意图、收据和检查点检查。
从持久的所有权记录中推导出资格，而不是一个可能丢失递减的裸计数器。第一个实现不需要全局 GC、TTL 租约、分布式协调器或自动定期删除。

### 迁移和证据读取器是工作的一部分

现有的本地目录早于pins。缺失的pins并不意味着没有消费者：
旧的输出默认仍然保留。首先对新创建的受管目录进行收集资格认证，使用记录的策略；旧目录需要单独的显式采用程序，而不是假设所有客户端都可见的扫描。未受管的读者除非操作员显式pins原始内容或移交一个独立保留的副本，否则没有保留保证。在该边界声明之前，拒绝收集。旧的宿主可执行文件不得操作需要新保留合同的存储；在删除之前，必须进行版本边界检查。

当前的接受、状态提交和因果验证可以重新读取原始负载。在删除任何本地负载之前，区分仅元数据的历史检查和仍需要字节的操作。保留所需的pins直到这些操作完成，并进行知晓墓碑的历史检查。不要全局弱化内容验证以使删除通过。负载垃圾回收是一个单独的操作；第一个产物收集器不得删除已提交的状态。

## 本地分发小组

```sh
an-agent-host cohort create WORKSPACE COHORT
an-agent-host cohort run WORKSPACE COHORT DISPATCH dispatch-request.json
an-agent-host cohort run WORKSPACE COHORT DISPATCH dispatch-request.json --approve HASH
an-agent-host cohort show WORKSPACE COHORT
an-agent-host cohort control WORKSPACE COHORT paused
an-agent-host cohort control WORKSPACE COHORT paused --approve HASH
```

现有 `session-create`、`session-run`、`session-show` 和 `session-control` 是别名。任一拼写均可批准另一的预览。两者返回相同的 JSON，包括历史 `session`、`thread` 和 `threads` 字段。
现有目录名、哈希值、磁带标签和收据保持其身份不变。
Rust 入口是 `events::cohorts`；`events::sessions` 仍为别名。

控制模式为 `open`、`paused`、`cancelled` 和 `closed`。每个控制变更都需要一个新的绑定摘要的预览。暂停请求会触发 drain-stop：一旦被观察到，执行器将完成当前条目并阻止下一个条目。控制响应确认发布，而不是跨所有执行器的同步屏障；条目在并发通过准入时仍可能开始。它仍被拥有且必须完成。
重新打开允许新的分发，从不恢复部分分发。
取消将永久关闭准入。每个活跃的受监督条目即使在有限控制器已退出的情况下也会观察其群体取消。关闭要求保留分发完成和原始确认尝试的证据。关闭永远不会接受产品、提交状态、释放引用、卸载实例或删除字节。

一个群体成员是一个不可变的有限分发（1..16 显式选择的事件/路由/状态条目）。它具有群体作用域的身份和持久的预执行意图。
更改源请求字节或群体生成将使批准失效。分发名称不能重复使用，包括在取消或缺少结果之后。宿主仅保留选定的产物/状态上下文，而不是其他 harness 的对话磁带。
父级、跨线程模型数据包和通用多尝试继续将被延迟。不会引入释放字段或 Loom 运行时依赖。

检查返回紧凑的身份标识和结果元数据；完整的调度证据仍可通过 `spool-events-dispatch-show` 获取，不会被复制到每个摘要中。
队列锁定仅覆盖短期的准入/控制发布。观察和执行不会持有该锁。有限控制器以 25 毫秒的间隔轮询其有界控制历史；这不是取消延迟的保证。读取错误请求取消，而非成功的结算。宿主崩溃后重新打开记录是只读检查：缺失的收据仍未知，且没有守护进程重启会执行或基于重用的 PID 发送信号。已死亡的运行器无法转发新的取消请求；原始后端的重新协调仍是必需的。

现有的事件准入锁仍保持快速失败。同一工作区中的同时准入可以拒绝；合格的情况明确允许独立的调度，并随后重叠其执行。它不声称队列或无冲突的并行准入。拒绝或未知执行不会自动重试。
限制为每个工作区 32 个队列，每个队列 3、2 个调度，以及 128 个控制记录。旧的可执行文件不管理这些队列记录；操作员发布的直接命令仍保持独立权限，不会被队列所追溯性地管理。

`tests/cli/native_sessions.py` 在宿主 crate 下支持独立重叠执行、作用域取消、drain-stop、过期生成/请求拒绝、多个命名调度、固定输入/状态、关闭后的产品以及真实执行后注入的丢失收据拒绝。它不使用任何模型调用。队列关闭重新检查本地证据；正式负载的垃圾回收仍被其独立未完成的保留合同所阻断。

## 前景监督者损失资格

原始的前景本地入口点在其启动 CLI 内保留其监督者。`OwnedChild` 在观察和终止其他组成员后，保持组领导未被回收，然后回收领导。原始绑定工作区收据记录该结果。普通错误和展开运行其清理守卫；SIGKILL 跳过守卫、取消轮询和墙上时钟截止时间。

`native_supervisor_loss.py` 使用两个有限工进程来实现实际的命令行界面。

| 故障 | 观察到的执行 | 管辖结果 |
| --- | --- | --- |
| 向启动 CLI 发送 SIGTERM | 原始监督者终止其组并记录取消 | 确认私有集合成功 |
| 向启动 CLI 发送 SIGKILL | 两个工进程存活，超过 3 秒的期限并完成写入 | 状态仍未确认；延迟输出无法被接受或收集 |
| 同样的终止装置且移除了陈旧操作锁 | 外部观察中没有存活的组 | 缺失的原始收据仍拒绝协调、收集、卸载和同次运行准入 |

该装置验证了独立实例可以运行，且之前接受的产品保持完整。有限工进程限制了实验的生命周期。进程样本和锁移除是可丢弃测试目录中的诊断故障注入。没有数字 PID、不存在的进程、不存在的锁或已完成的输出文件都不能确立原始监督者的所有权或恢复丢失的执行结果。

## 独立尝试监督者

显式的 `spool-supervisor` 条目拥有一个原生文件、检查点或结合业务数据/状态的运行，该运行在一个独立的进程中。它使用相同的已审查的 spool 发布、批准的启动计划、执行边界、进程组结算和正式的产物命令。

```text
spool-supervisor start INSTANCE RUN INPUT SECONDS [--approve HASH]
spool-supervisor start-state INSTANCE RUN REVISION SECONDS [--approve HASH]
spool-supervisor start-data-state INSTANCE RUN SELECTION_JSON SECONDS [--approve HASH]
spool-supervisor show INSTANCE RUN
spool-supervisor cancel INSTANCE RUN [--approve HASH]
spool-status INSTANCE RUN
spool-reclaim INSTANCE RUN [--approve HASH]
```

预览绑定规范输入、可执行文件、实例、发布、激活生成和原生启动计划。批准永久保留运行在生成分离监督进程之前。工作者必须独占请求，然后在启动任何域进程之前重新验证原始原生计划。直接启动也拒绝保留的身份。一个撕裂的保留或所有者声明仍然被封锁。客户端超时、缺失响应或启动失败永远不会重试。

工作者拥有原生进程组和截止时间。客户端等待其响应，并将处理的信号作为持久取消转发。突然的客户端丢失会使执行在完成或原始截止时间之前继续受监督。另一个操作员CLI可以请求取消特定请求，而无需获取实例执行锁。控制位于宿主私有运行目录中，超出域进程写入权限。不可读的控制标记请求取消。PID字段仅用于诊断；控制从不发送记录的数字PID。

监督进程在执行后停止并写入与请求绑定的响应。原生结算仍然是接受和收集的权威。监督进程退出、响应文件或取消请求本身并不赋予控制权。监督进程崩溃会导致未解决的记录，并在观察到进程退出后仍阻止收集。丢失的客户端可以检查原始运行，而无需重新启动它。

一个在工人准入之前发布的取消操作会被同步检查。原始工人可以在不重新读取已不可用的输入的情况下确认`cancelled-before-launch`。圆闭/卸载需要其匹配的请求、独占所有者和精确的无启动完成，同时不存在任务、启动、输入引用和托管记录。仅有一个取消请求或任何矛盾/不完整的记录都保持不确定性。这会关闭一个未使用的保留；它既不授予产物接受也不授予收集，且永远不会允许重放。
`native_spool::prelaunch_cancel` 使用真实的工人 CLI 来执行这个确定性边界，包括已移除的输入、缺失/不匹配的证据、重复的工人拒绝以及保留早期接受的产品。

`native_supervisor.py` 通过持续的期限和取消强制执行来符合客户端 SIGKILL，处理客户端 SIGTERM、重复工人和过期控制拒绝，一个撕裂的启动保留、监督者 SIGKILL、一个独立实例以及保留正式产品。其有限的工人限制故障实验。原始前台故障案例仍保留在 CI 中以保留其显式限制。

显式的状态监督使用`start-state`并具有精确的检查点修订。修订和原生启动计划被绑定到持久批准中，工人通过现有的状态输入路径再次选择该修订。推进 HEAD 永远不会选择不同的检查点。真实的状态故障套件在启动旧修订之前推进 HEAD，并测试客户端丢失、超时、取消和未知所有者保留。其`--combined`模式会使用独立的业务数据和状态重复故障矩阵，包括过期选择器拒绝和保留精确的输入引用。

组合监督使用`start-data-state`与现有的选择JSON。
审批保留已解析的原生计划和两个精确绑定，而不是可变的selector路径。工作者在启动前重新验证这些修订和准入；在保留之后，无法重新定位selector的替换/移除。一个退休的输入会失败关闭，没有回退或新尝试。一个确定性的实际执行测试覆盖了selector的移除和退休在保留和工作者声明之间。

## 路由执行所有权

正常的原生CLI为每个批准的事件交付或对等执行阶段提供相同的单次尝试监督器，如同受监督的文件和状态启动一样。审批包括已安装的宿主可执行文件、交付或对等阶段身份、精确的产物/状态选择以及任何拥有有限分发或群体。一个独立的事件需要其自身的审批。
直接的Rust嵌入函数可以保留调用者拥有的执行。狭窄的受监督CLI路径使用已安装的宿主本身来运行工作者。

一个额外的短命控制器拥有每个显式批准的批次或群体分发。一个群体分发会重用其控制器用于其嵌套批次。控制器读取已准入的选择，检查每个原始条目授权，并一次启动一个尝试监督器。提交的CLI等待原始结果。在所有者启动后，它强制执行截止时间，并且即使客户端退出也接受控制。在保留和所有者启动之间发生崩溃会导致原始保留未解决并被保留以供检查。删除操作员的原始选择文件无法改变已准入列表。等待对等回复不会创建工作者。
每个对等请求及其响应都需要其自身的执行审批。

```text
spool-supervisor show RECEIVER_INSTANCE RUN
spool-supervisor cancel RECEIVER_INSTANCE RUN [--approve HASH]
spool-supervisor dispatch WORKSPACE BATCH show|stop|cancel [--approve HASH]
spool-supervisor dispatch WORKSPACE COHORT DISPATCH show|stop|cancel [--approve HASH]
```

旧的 `spool-supervisor thread` 拼写对队列成员仍然有效。
Show 不需要审批。Stop 会耗尽当前条目并关闭列表的剩余部分。Cancel 也表示已接受的尝试。队列范围的控制命令保留其原有的作用域。一个尝试会直接观察其父级的持久化取消。对等协议取消会关闭未来的请求/回复准入。接收方宿主可以通过其实例和运行来取消一个活跃的对等阶段。控制确认确认请求的发布。

缺少控制器完成会使批次或队列分发保持未解决状态。一个已经接受的子项保留其截止时间，并且仍可以被取消。没有后续控制器会继续处理剩余条目。失去尝试拥有者会使进程组未确认；托管需要绑定的本地接收 **和** 路由拥有者的原始完成。经过验证的超时或程序失败会以该结果结束有限的选择。队列关闭、成果接受和事件确认仍然是独立的操作。

真实的无头套件会在事件、批次、队列分发和两个对等阶段期间终止提交的 CLI。它也会独立地终止控制器和尝试拥有者。测试覆盖了超时、作用域取消、耗尽停止、过期授权、缺少接收和拒绝继续不确定的工作。前台 `spool-start` 故障情况继续验证该入口点的限制。本地监督员记录和安装的宿主是可信的。宿主重启后的自动恢复不在该合同范围内。

## 运行时控制和传统会话兼容性

目标激活记录绑定一个实例/发布、生成、拥有的尝试引用、端点引用和操作者拥有的限制。重用现有的尝试标识，而不是添加第二个执行账本或操作系统线程调度器。当支持时，提供者/框架会话 ID 是不透明的私有适配器数据。它们既不是 spool ID 也不是新的权限。不要摄入私有框架磁带。

使用以下生命周期区别，而不是一个被重载的状态：

- 入口是开放的或暂停/关闭的；暂停仅阻止新工作。
- 执行状态为运行中、结算中、正结算或未知，由原始尝试的证据推导得出。请求取消并不代表确认。
- 一个队列在它的自有工作完成收尾完成后可以关闭；未解决的工作仍可见，并阻止成功关闭的结果。归档其视图并不代表可以终止进程或删除产品。

一个队列范围的停止会在将取消请求转发给一组特定的、生成绑定的自有活动尝试之前关闭入口。停止和取消仍然是独立的：停止会处理已有的工作；取消请求终止。两个会话必须保持独立。单一因果协议链接无法取消另一个会话的工作。参考释放和临时清理仍然需要各自原始的证据。

中断后，重新打开记录并检查尝试，再提供新的工作。恢复一个核心对话不会恢复原生命令。一个新的执行需要一个新的尝试和显式的输入/检查点/授权选择。未知的旧工作不能通过创建新的会话或线程来重试。延迟的结果绑定于其原始尝试/生成，不能声称新工作的输出。在没有测量需求的情况下，不要添加操作系统线程池、伪终端或空闲模型会话。

## 响应性与令牌纪律

快速路径是确定性的：检查身份/状态，路由一个持久事件，检查授权，选择引用并调用现有CLI。不要为轮询、统计待处理工作、复制文件或常规生命周期决策而调用模型。

- 默认发送引用和压缩后的结果元数据。仅在获得批准的受众和具体任务下获取精确内容。引用不表示读取授权；解析引用时必须重新检查访问权限和保留状态。
- 保持完整的接受输出与面向模型的受限视图分开。在引入生成的摘要之前，应重用已有的已验证出口内容。
- 选择指令、当前目标、精确的相关输入/状态、待决决策和必要的错误片段。不要发送整个记录或无关的线程。权威性、未解决的失败和批准范围绝不能通过静默截断而消失；在必要时拒绝或请求更小的选择范围。
- 派生的摘要为一次性、不可信的上下文，包含源修订/范围、策略/版本和遗漏元数据。它不能成为权威状态、权限或成功证明。根据保留策略保留原始内容。
- 仅在匹配源身份、受众、策略和选择参数的情况下重用选择内容。重新检查授权；去重不能仅仅因为负载字节匹配就合并两个不同的业务事件。
- 仅合并一次性进度通知。保持持久化成果事实、取消、错误和所需确认信息的独立性和有序性。
- 仅在适配器能证明其正确身份和范围的情况下重用现有框架上下文/会话。取消和未知提供者结果绝不会触发模型的自动重试或备用提供者。

初始限制是明确的字节数、项目数量和并发数。不要将字节重新标记为标记。精确的标记/花费执行需要提供者特定的使用和计费；未知使用记录为未知，而非零。在测量质量和实际使用之前，不要承诺提示缓存或摘要带来的节省。

## 交付顺序和接受

| 切片 | 可交付成果和结束条件 |
| --- | --- |
| A: 原生制品所有权 | 新管理输出通过真实生产者/双消费者执行获取/释放显式引脚；活跃和未知的所有者、保留的检查点依赖项和遗留目录会阻止删除；遗留输出保持保留 |
| B: 正式负载收集 | 闭合准入加上释放引脚允许精确批准的删除；保留的血缘关系仍可检查，内容读取会明确失败，无关输出/检查点存活；竞争、取消和丢失删除接收拒绝不安全进展 |
| C: 运行时所有权 | 显式监督输入、路由尝试和有限控制器在客户端丢失时保留批准的工作。缺失原始所有权证据会阻止执行和保管。 |
| D: 有界上下文交接和组合资格 | 原生对等请求通过真实监督执行对受众绑定的数据包进行资格认证。配对的打包案例将作用域字节与保留和中断结合。一个声明释放的核心代理可以接收剪辑；模型 CLI 需要单独的披露批准。 |

A 和 B 关闭了剩余的 P1 存储合同。C 和 D 是下一个小型管理里程碑，不是无限制扩展 P1 的许可。GUI/TUI、通用对话引擎、语义搜索/GNN 路由、提供者目录、GPU/VM 挂起和自动状态迁移仍不在范围之内。

Slice A 是部分的：新的本地启动将注册精确的 artifact/checkpoint 输入。
已确认取消的所有者可以在私有集合后释放；成功的无状态事件消费者可以在原始消费确认后释放，已验收的输出和私有集合。成功的组合数据/状态事件所有者可能在获得与提交的 checkpoint 相关的全面覆盖批准后释放其临时权利。
部分注册和旧的/未管理的读者仍被保留。显式的 checkpoint 依赖声明现在获得不可释放的源引脚；缺少注册证据会阻止选择。其他成功的所有者路径、依赖关系退休/协调以及混合宿主版本围栏仍不在可选注册复制集合配置文件之外。目前没有参考查询授权删除。
生产端的 `spool-artifacts ... --references OUTPUT` 观察现在暴露了注册消费者，而无需控制锁。源释放标记与消费者完成分开报告；空视图永远不会是完整的普查。

使用 Rust 测试进行内部转换/竞争窗口，使用 Python 进行真实 CLI 验收。Loom 保持一个窄的包到宿主兼容性案例；它不会复制宿主的故障矩阵。不需要实时模型来证明生命周期或确定性上下文选择。Fixture 使用仅证明协议处理；如果需要，分别报告后续的实时提供者测量。

记录输入/释放/二进制标识符、尝试、事件、引脚转换、结算和删除收据、进程计数和逻辑存储字节。测量事件到准入和取消到确认的延迟、上下文选择时间、发送字节、实际提供者使用情况（如可用）、模型调用次数、人工干预和峰值存储。将冷/暖运行分开并记录构建/运行时间。仅在样本数量和足够样本的情况下报告 p50/p95；小规模运行列出原始值。APFS 逻辑减少并非物理回收空间。在不削弱结果检查的前提下，将相同工作负载在前后进行比较。确定性路径必须要求零模型调用；定量延迟/令牌目标应遵循基线，而非虚构的百分比。
