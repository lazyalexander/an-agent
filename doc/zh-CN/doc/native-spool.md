内容标签遵循 [修订版 2 合约](spool-code.md)：每个发布文件都是 silk，包括位于历史 `kit/` 路径下的文件。可变衍生品和新工作是 kit。下面的路径绑定描述的是合格的旧版配置文件，而不是这些标签的定义。指令资源保持受保护；标签不授权新文件、配置更改或执行。

## 与发布绑定的原生 spool：已审核的无头配置文件

状态：已为已审核的本地 shell 工具和显式选择的 [原生 Python 环境](native-spool.md) 实现。这是一个受限的 spool 外壳，覆盖现有的工作区监督员、快照和保管机制。平台覆盖范围在 [运行时矩阵](platforms.md) 中保持不变。它不是任意的代理沙箱、通用依赖解析器或替代受信任的进程内 `SpoolBeat` 挂载。没有引入核心或 Loom 运行时依赖。领域序列化仍保留在入口 silk 中。

可选的 [显式原生状态](native-state.md) 将选定的检查点绑定到运行，并提交一个接受的状态输出，同时进行版本检查。它使用相同的发布；v3 可以选择独立的数据和状态输入。普通运行保持无状态。

[轮次边界控制](native-spool.md) 在确认收尾完成后暂停准入，固定一个检查点用于暂停，并显式重新开放准入。它不会暂停或恢复正在运行的进程。

[原生存储](native-storage.md) 将工作收集与私有输入快照收集和正式状态/产物保留分开。它还增加了原生工作区准入的缓冲空间，而无需运行时文件系统配额。

[发布审查](native-state.md) 比较精确验证的包字节和请求的合约，而不授权更新。候选延续使用一个全新且独立批准的实例；旧发布和状态仍被保留。

[原生工作区事件](native-events.md) 增加了显式的 v3 事件接口和宿主拥有的产物分发。V1/v2 发布保持不变，不会隐式获得事件权限。业务序列化仍保留在 silk/kit 内部。

[原生 Python 和二进制产品](native-spool.md) 添加了操作员选择的、库存绑定的依赖项和显式的字节输出到 v3。V1/v2 和现有的 shell 包保留其行为；没有任何包执行依赖项安装。

### 合约和布局

Loom 的 `export-native-spool` 导出 `native-spool.json` 和选定的 `silk/` 和 `kit/` 文件。任何生产者都可以发出此版本化的 JSON 合约；宿主独立验证它。这个新合约不会重新解释现有的 `spool.yaml`、`file-kit-v1`、`[silk]` 或旧版 `[kit]` 格式。

清单文件包含确切的 `schema`（`an-native-spool-v1`）、`name`、`version`、`entry`、`files`（相对于 SHA-256 的代码路径）和 `outputs`。代码路径包含一个角色目录和一个 ASCII 基名，该基名在两个角色中都是唯一的。入口必须是一个声明的 silk。最多允许 12 个代码文件，每个文件 1 MiB，总计 8 MiB。输出为 1–16 个不同的顶层文本文件名，不包括 `kit` 和 `tmp`。现有的文本输出和工作区库存限制仍然适用。名称/版本标签不认证发布者，不建立更新血统或暗示 SemVer。发布摘要对确切的清单字节进行哈希，并传递性绑定代码。未知字段、未列出的文件、符号链接、硬链接的负载和不匹配项将被拒绝。

仅加载会创建一个新的实例目录，并复制经过验证的发布内容以及单独的 kit 工作副本。不会运行任何包代码或安装钩子。实例 UUID 与发布摘要不同。所有文件仍由宿主拥有；工作负载不能写入实例存储、基线、配置文件或权限数据。

```text
INSTANCE/
  instance.json
  release/native-spool.json, release/silk/*, release/kit/*
  kit/*                         # edit between runs through host approval
  round-control.json            # optional admission mode and generation
  round-control/*               # immutable transition evidence and staging
  runs/RUN/
    profile.json, start.json, result.json
    accepted.json, reclaimed.json   # bound custody results when present
    job/                        # existing private workspace execution layout
  unloaded.json                 # terminal load lifecycle marker
```

一个负载并不是对旧嵌入式注册表的注册。这个切片将一个已验证的包直接绑定到一个新的宿主实例。重新加载使用一个全新的实例目录；现有的实例及其证据不会被覆盖。在源发行目录下进行加载会被拒绝。每个实例最多分配64个运行名称。已使用的运行名称永远不会自动重试。


编辑、启动、接受、回收和卸载首先返回一个计划和审批摘要。启动预览可以持久化一个有界的配置文件，但不会真正启动。启动审批绑定实例标识、发布、运行名称、所选工具箱/输入哈希值、有效的本地策略和截止时间。在输入或工具箱更改后重用审批将失败。加载和显示不会创建执行权限。

固定运行时为 `/bin/bash`；`entry` 选择一个脚本，而不是宿主可执行文件或额外的命令行授权。依赖项是现有的已审核的 macOS 运行时闭包，而不是一个赫尔metic 打包的工具链。网络仍然被拒绝。Silk 看到：

- `AN_SPOOL_SILK_DIR`：只读的选定代码快照目录。
- `AN_SPOOL_KIT_DIR`：相同的只读目录，包含选定工具箱的版本。
- `AN_SPOOL_INPUT`：选定的、固定版本的输入文件。
- 当前目录：用于中间文件和输出候选的可写工作区。

工具箱编辑只影响已加载实例的工作副本。启动将这些字节固定到一个新的执行快照中。运行时的编辑会被实例操作锁拒绝；没有实时自我编辑的协议。一次新鲜的加载会恢复包基线。生成的工作文件保持为临时文件，不能改变规范的 Silk 或选定的代码快照。这并不能证明被破坏的解释器会遵守域序列化：任意的敌对本地进程树仍然不受支持。

### 生命周期和制品所有权

一个活跃的操作持有每个实例的锁。独立的实例使用不同的锁和工作区。发送 SIGINT/SIGTERM 到正在运行的宿主 CLI 会通过现有的监督者请求整个尝试的取消。没有仅基于数字 PID 的控制 API、后台服务或持久化的取消邮箱。

结果信封绑定实例、释放、运行、配置摘要以及精确的原生接收凭证。托管服务重新检查这些字段以及现有的终止证据。另一个实例的接收凭证不能声称该实例的输出。产品仍保留在运行下的现有不可变产物目录中；卸载不会删除它们。下游固定检出仍使用 `artifact-checkout CATALOG REVISION PATH`；没有活跃的共享可写产品目录。

卸载拒绝主动或未确认的尝试。它释放对新工作的准入，而不是磁盘内容或正式产品保留。每个运行的显式回收仍保持独立，并在卸载前后工作。它仅在现有结算/接受门限之后放弃工作/恢复权利。新的 `archived_record` 读取检查集合意图、接收摘要和最终标记，以识别之前收集的运行；普通工作空间准入在GC后仍被限制。输入和诊断证据保留其现有策略。没有引入自动GC、磁盘配额执行或无限历史承诺。

被终止的宿主、缺失的结果、过期的锁或部分发布仍保持明显不确定且被限制。没有自动锁移除、重启或接收凭证修复。存储被信任以防止同用户篡改，如同现有的宿主配置文件。

### 合格接受

`tests/native_spool.rs` 实现真正的原生隔离、两个silk步骤、编辑的工具包、禁止silk/外部写入、两个并发实例、取消、主动操作拒绝、跨实例接收凭证替换、收集/卸载后的不可变产品检出、重复运行拒绝以及新鲜加载基线恢复。相邻单元测试覆盖非执行/独占加载、更改的负载、未列出的材料和包尝试请求额外权限。

Loom 分别针对固定宿主版本运行一个真实的CLI往返。它导出实际的示例存档，编辑工具包，执行，接受，回收，卸载并加载一个新鲜实例。两个仓库不会互相链接运行时。

### 当前扩展和剩余范围

[状态页面](status.md) 包含当前的 P0/P1 计划。显式检查点延续、回合边界暂停/挂起、私有快照收集/预留空间、事件分发和接收者继任均实现了有界合约，而非未来阶段。下方的宿主提案槽仍为文件交换；可选的已审查的 harness 开发属于 Loom/Weaver，而非新的宿主模型循环。进程内存暂停/恢复、自动状态/释放迁移、形式化负载 GC 以及更强的敌对进程隔离仍不达标。不要从准入控制或后端能力标志中推断这些保证。

托管运行携带一个 `spool-owner.json` 标记。公共独立工作区运行、接受和回收命令拒绝这些任务；调用者必须使用所属的 spool 命令，以确保实例操作锁和所有权检查持续有效。这是一个 API 生命周期边界，而非防止宿主用户修改控制存储的保护。

### 可选的工具提案槽

宿主现在暴露的是一个文件交换槽，而非模型循环或插件启动器：

```text
spool-kit-proposal-request INSTANCE KIT_BASENAME
spool-kit-proposal-apply INSTANCE PROPOSAL_JSON [--approve HASH]
spool-kit-proposal-revoke INSTANCE REQUEST_UUID
```

一个请求返回 `request` 和 `request_sha256`。所选的请求携带实例、发布、套件路径、原始内容哈希和来源，以及从运行和编辑身份推导出的纪元。仅接受声明的套件基础名。外部 CLI 适配器或授权的 shuttle 可以读取该导出数据并返回：

```json
{
  "schema": "an-weaver-proposal-v1",
  "request": "REQUEST_UUID",
  "request_sha256": "HASH_FROM_REQUEST",
  "kit": "kit/transform.sh",
  "content": "printf 'adapted:'; cat \"$1\"\n"
}
```

操作员导入响应。宿主在实例锁下检查其作用域、生成和字节，然后预览一个独立的审批。提案不是一种能力令牌。不要将不受限的宿主CLI或其私有控制存储暴露给代理。传输适配器仅负责传输选定的数据；穿梭传输无法授予权限。

任何运行准备或记录的套件编辑都会使之前的请求失效，即使编辑恢复了相同的字节。撤销会关闭结果准入，但明确不声称外部代理已终止。卸载/重新加载会更改实例身份。请求是一次性使用的，限定为128个目录条目；应用程序在编辑前通过提交意图关闭请求。中断的导入会失败并关闭，需要检查而非重放。没有引入自动清理。

`weaver_proposal_slot`在能力中为真；`weaver`保持为假，因为没有启动或监督任何框架。真实的跨仓库测试使用的是确定性的文件提案，而不是模型。宿主测试还涵盖了被撤销/过期/外部请求、受保护的silk、更改的提案批准、重复的应用以及固定版本的产物检出到第二个存储区。这不会引入任何新的领域或模型依赖。

### 准备就绪时间与CI

CI将测试编译和执行显示为独立的步骤，不排除任何工作区测试。64 MiB克隆交接回归测试运行五个变异/取消案例。其准备就绪时钟包括准入哈希和快照准备；它与工作负载的30秒执行截止时间是不同的。120秒的准备就绪看门狗是一个有限的测试预算，而不是产品延迟保证。失败会取消并加入工作者，并报告其结果。当`AN_AGENT_ACCEPTANCE_DIR`被设置时，现有CI产物步骤会在`clone-handoff/`下保留每个案例的准备就绪/完成证据。文件大小、固定版本断言、取消检查和生产截止时间保持不变。准备就绪性能仍保持为可测量的后续工作。

规范模块是 `native_spool::kit_proposal`。旧的 `weaver` 模块、
`spool-weaver-*` 命令、`weaver_proposal_slot` 功能、磁盘上的 `weaver/`
票据和 v1 架构保持兼容。`kit_proposal_slot` 宣传规范名称。此插槽接收编辑；它不准备 harness 任务，
不审查生成的代码或启动代理。这些未来角色使用 Weaver 名称。

### 显式原生 v2 要求

宿主也接受 `an-native-spool-v2`，包含 v1 字段加上一个必需的
`requirements` 对象。v1 带有要求和 v2 不带要求的拒绝。初始允许的值包括运行时 `macos-native-process-v1`、OS `macos`、
架构 `portable-source`、交互 `headless`、GPU `none`、一个便携式
文本输入插槽名称、无额外依赖项，以及正好是功能请求的 `read-input` 和 `write-declared-outputs`。可编辑路径必须是
唯一选择的套件路径；与旧版 v1 不同，套件负载不是隐式可编辑的。

准入在实例创建之前发生，并在读取发布以执行时再次检查。不支持的目标/GPU/应用程序要求、未知
功能和未解析的依赖项将被拒绝；它们永远不会选择较弱的后端。显示报告请求的功能，而启动批准绑定的
实际固定工作区策略。功能标签不授予权限。v2 目前仅限 macOS。Linux 包装和未来后端合同必须
不要与合格执行混淆。GPU CLI 执行和 shuttle 介导的应用程序交互是独立的功能；这里均未实现。

### 发现已验收的产物版本

`spool-artifacts INSTANCE RUN` 是一个只读的宿主查询返回实例，包含发布、运行、制品目录和固定输出版本绑定。它需要确认结算和匹配的本地/工作区接受记录，验证接受的库存以及每个保留版本的字节和来源，并且不会推广临时文件。在临时文件回收和实例卸载后，它仍然可用。使用现有的制品检出功能来实现下游输入所选版本。不会引入可变的最新指针。

Loom 仍然在发布中声明输出，并不拥有运行时目录。该命令适用于本地 v1 和 v2。缺少接受记录、不确定的终止、外部记录和内容变更将被拒绝。现有的文件名或成功的退出本身并不能确立正式的制品。

### 运行监控

`spool-status INSTANCE RUN` 是一个仅观察的查询。它返回一个稳定的阶段（`prepared`、`unconfirmed`、`running-or-unconfirmed`、`settled`、`accepted`、`reclaimed`）、执行结果、终止确认以及单独的制品状态。缺少、不一致或竞争的结算仍然不确定。收集需要经过验证的工作区证据；仅外层标记无法确立它。已已验收的输出绑定使用与 spool-artifacts 相同的证据检查，并且在卸载后仍然有效。部分接受将被报告为未确认，而不是干净的待处理状态。

查询从未获取、写入或清除实例执行锁，包括在验证接受输出时也是如此。一个繁忙或过期的锁本身并不能使有效的产物证据未确认。查询从未从PID或锁文件推断出活动性。缺失的收据无法区分正在运行的工作与中断的记账。所有变更/保管命令独立地重新验证并保留其现有的锁和批准。响应是一个有界的观察，而不是一个原子的调度决策。

首先合格的是无头CPU。常见的调度/监控身份可能被重用于未来的GPU/应用后端，其实际支持的生命周期和外部结算必须分别进行资格认证。这些状态名称中并未暗示暂停或挂起的支持。

### 恢复中断的接受交接

如果工作区接受已完成，但记录实例绑定的accepted.json失败，状态报告未确认的保管，普通接受不会重试。
`spool-reconcile-accept INSTANCE RUN [--approve HASH]` 展示了一个修复过程，验证确认的结算，完成工作区接受，精确的输出清单以及所有保留的版本/来源，然后仅写入缺失的实例记录。一个匹配的现有记录是一个显式验证的无操作。冲突、不完整、外来或更改的证据将被拒绝；现有记录绝不会被覆盖。

批准绑定完整的恢复接受绑定。没有工作负载被重新启动，也没有产物被重新发布。查询和下游检出工作将再次使用原始修订版本。这不会恢复不完整的工作区接受或缺失的执行结果，清除不确定的终止状态，或推断外部工作者已停止。这些状态将被保留以供后续的协调。
文件系统故障验收测试执行实际发布后跟一个失败的外观写入；这不是对任意断电耐久性的声称。


### 恢复可编辑的套件基线

`spool-kit-reset` 从已验证的发布基线中恢复一个已声明的可编辑工作副本，而不改变实例标识、保留产品或其他工具包。预览和批准使用现有的编辑计划及其前后摘要。它与 update-kit 共享相同的实例锁、可编辑路径检查和编辑收据；处于活动执行中的实例和未加载的实例将被拒绝。受保护的 silk 或不可编辑的 v2 工具包路径仍然禁止。不可变的发布不会被修改。

当重置更改工具包字节时，之前针对不同字节的启动批准将失效。每个已批准的重置记录一个编辑生成版本，因此即使经过编辑离开/编辑返回的循环，旧的提案仍会保持过时状态。它不授予执行权限。需检查并单独批准下一次启动。现有的加载/卸载/新目录基线恢复仍有效。

### 修复缺失的执行结果

`spool-reconcile-run INSTANCE RUN [--approve DIGEST]` 明确修复一个缺失的 outer result.json，当一个完整的 workspace 尝试已经确认进程终止时。它验证实例/发布/运行的所有权、原始启动计划、配置文件标识、workspace 意图、收据、执行映射和快照字节。在批准后仅写入派生的结果记录。匹配现有记录被视为已验证的无操作；冲突记录永远不会被覆盖。

尝试发现需要恰好一个规范的 UUID 目录。一个普通的 `.DS_Store` 文件将保持原样，并被列在修复批准的 `ignored_attempt_entries` 中；它不是一个尝试。其他意外条目、链接、非规范 UUID 名称以及名为 `.DS_Store` 的目录将被拒绝，并带有诊断信息命名该条目。多个真实尝试仍然模糊且被拒绝。不应用任何通用的元数据或编辑文件排除规则。

这不会启动、重试、接受输出、清除锁或从PID推断终止。缺失/不确定的接收确认、未启动的尝试、多次尝试、更改的快照、外部绑定和回收的工作区将被拒绝。保留这些状态以供调查。修复后的成功运行仍需要显式的spool-accept；失败/取消的运行仍不可接受。正常的回收/卸载只有在满足现有证据检查的情况下才可用。

真实的文件系统故障测试会在目录阻止最终结果写入的同时完成成功和失败的工作负载。然后它们会验证显式的修复、无需额外尝试或发布、负证据情况和正常保管。这不是任意的崩溃恢复或断电持久性声明。

## 圆边界处的原生控制

第一个控制切片使用一个已完成的spool尝试作为其安全点。它在尝试之间暂停准入；它不会停止正在运行的进程。spool作者决定域工作如何达到已提交的检查点。宿主验证终止、已已验收的输出和固定的标识，而不解释状态。Loom打包相同的v1/v2版本；不需要新的版本架构或后端。

```text
an-agent-host spool-pause INSTANCE [--approve HASH]
an-agent-host spool-suspend INSTANCE STATE_REVISION [--approve HASH]
an-agent-host spool-resume INSTANCE [--approve HASH]
```

每个转换都有一个预览和独立的审批。正在进行的操作、过期的锁、未知的终止或成功运行但缺乏正式接受的都会被拒绝。准备好的计划不视为执行；中断的启动且没有完成的工作区证据也不视为执行。没有任何东西可以清除过期的锁或重试执行。

暂停会阻止新的启动、套件/提案应用和状态变更。检查、提案撤销和现有受保护的产物保管仍然可用。暂停还会固定当前提交的文本检查点和有效的套件哈希。它保留状态、释放和证据；在结算和接受后，可以通过现有命令显式回收临时空间。

恢复在重新打开准入前会验证保存的释放、套件、检查点和完成运行的证据。它不会启动任何内容，也不会继承旧的执行审批。继续仍然需要显式选择`spool-start-state`并获得新的审批。一个域可以选择开始单独授权的新工作。不会隐式注入状态、程序计数器、堆或隐藏的临时空间。

控制生成防止在暂停/恢复周期后旧的启动和转换审批再次生效。转换在原子地更改控制头之前会发布不可变的证据。中断的发布会保留之前的模式；显式重复相同的已批准转换可能会完成其发布。对已发布的转换的确认是一个无操作。不兼容的阶段记录会拒绝检查，而不会覆盖历史记录。这不会建立突然断电恢复或恶意宿主存储的安全性。

`spool-show`会将模式和生成分别报告，与运行的结果分开。现有的`spool-status`继续描述执行和保管，无论是否暂停了新工作。卸载仍然是终端的，保留检查点和控制证据，并且可以从已结算的暂停/暂停实例中允许。一次新鲜的加载使用现有的显式固定状态检出/种子路径并恢复套件基线；它不是自动的实例或进程恢复。

现有的实例如果没有控制头，则从活动生成零开始。第一次批准的转换安装基线，而不改变发布标识。在发布任何停止的准入模式之前，它会将私有实例记录原子性地升级到`an-native-spool-instance-v2`。较旧的宿主拒绝该记录，而不是静默地忽略控制；支持此功能的宿主继续读取旧版 v1 实例。这是实例格式的下限，而不是发布格式的更改或防止操作员故意重写私有存储的保护。安装后缺少或不一致的控制证据会阻止准入。通用的暂停/挂起能力标志保持为 false。单独的`pause_between_attempts` 和 `suspend_checkpoint` 标志描述此 macOS 切片。正在进行的协作信号、透明进程挂起、虚拟机快照、GPU/GUI 后端和自动存储收集仍不达标。

## 操作员选择的原生 Python 和二进制产品

状态：适用于已审查、仅 CPU、无头工具；平台覆盖在 [运行时矩阵](platforms.md) 中保持。这通过现有的工作区执行和二进制产物保管扩展了 [原生 v3 事件配置文件](native-events.md)。它不添加任何核心依赖项、环境安装程序、包解析器、代理框架、域解析器或每 silk 的额外隔离。

### 可移植请求和本地选择

一个原生 v3 发布可以声明 `binary_outputs`，这是 `outputs` 的一个独特子集。省略保留文本输出行为。每个二进制输出均通过现有的产物-v2 协议作为不透明字节接受：每个文件 8 MiB，合并输出 16 MiB；文本保留其 UTF-8/64 KiB 的限制。格式、公式、ZIP 扩展和域检查属于消费者。文件扩展名不选择编码。较旧的 v3 宿主拒绝新字段，而不是静默地将其接受为文本。V1/v2 字节和行为保持不变；它们不能声明二进制输出。

需求可能仅在 v3 中选择 `macos-native-python-v1`，使用现有的 macOS、portable-source、headless、GPU-none 以及 exact 能力请求集。仍支持单个文件输入。其声明的槽位名称将成为快照名称，因此消费者可以从存储为 `content.bin` 的制品中接收 `source.xlsx`。
代码基名和输入名称必须不同。可选的 v3 `state_input` 增加了一个通过 [data/state contract](../../native-state.md#independent-business-data-and-state) 单独选择的检查点。它会获得自己的快照名称和 AN_SPOOL_STATE 路径。没有基于扩展的分发或隐式状态/输入合并。

该发布包含有界的唯一依赖项标签，而非可执行路径、安装钩子或权限。操作员单独选择兼容的环境：

```text
an-agent-host spool-load DELIVERY NEW_INSTANCE --runtime RUNTIME_JSON
```

严格操作符 JSON 具有这些字段：

```json
{
  "schema": "an-native-python-runtime-v1",
  "executable": "/selected/python/bin/python3",
  "executable_sha256": "EXACT_SHA256",
  "stdlib": "/selected/python",
  "site": "/selected/venv/lib/python3.12/site-packages",
  "site_sha256": "EXACT_INVENTORY_SHA256",
  "dependencies": ["example-1.0.0"]
}
```

路径必须已经是规范化的绝对路径。`stdlib` 和 `site` 是两个独立的目录，位于发布版本和实例目录之外；根目录、符号链接和嵌套选择会被拒绝。依赖项标签必须与发布版本完全匹配。Shell 发布版本拒绝未请求的运行时；Python 发布版本在创建实例前拒绝缺少绑定。Load 会将选定的 JSON 复制到只读的 `runtime.json`，并在 `instance.json` 中绑定其精确的摘要，并不执行任何解释器、项目钩子或安装程序。Start 仍然需要其自身的批准。Loom 永远不会提供或批准此机器本地的绑定。

站点库存是紧凑 UTF-8 JSON 映射的 SHA-256 值，该映射将排序后的相对 POSIX 文件路径映射到 SHA-256 内容摘要。所有文件，包括字节码，都会被包含。符号链接、硬链接、非常规文件、超过 8,192 个条目、深度超过 16、超过 20 MiB 的文件或总字节数超过 256 MiB 的文件会被拒绝。宿主在检查包时不会导入包。标签是操作员的断言；它们的相等性或内容哈希值不会验证包发布者或认证安全性。

### 执行与接受

现有的工作区监督者使用选定的解释器运行 `-S -B`，尝试私有代码/数据快照，并且不带环境变量。`PYTHONPATH` 仅指定了选定的快照和站点目录。用户站点初始化、`.pth` 启动处理和字节码写入被禁用。`HOME` 和 `TMPDIR` 指向工作区的临时空间；选定的运行时根目录是只读的，网络访问仍被已审查的本地策略拒绝。操作员绑定摘要包含在已批准的执行环境中。

解释器的摘要和依赖项清单在加载时、计划批准启动时以及在本地构件接受之前都会重新检查。更改的依赖项不会默默地更改环境、启动替换尝试或接受其输出。请显式地恢复/重新选择一个有效的环境；未知的执行绝不会自动重试。
标准库和系统动态库仍然是操作者拥有的平台依赖项，而不是不可变的打包快照。预/后检查并不能防止恶意的并发同用户更改和恢复攻击。这是现有的已审查工具边界，而不是任意的恶意代码隔离。
本地构件的发现和收集依赖于保留的执行/托管证据，而不是持续安装Python。已接受的二进制构件和消费确认在工作/快照收集、实例卸载或运行时丢失后仍然可读。未接受的成功工作将保留，直到其接受边界可以解决为止。
二进制事件使用与文本事件相同的精确完整版本绑定。交付选择`content.bin`用于验证的字节版本，并将版本带入工作区输入溯源。它永远不会跟随可变的最新指针。显式的接受和消费完成仍然与成功执行分开。
### 合格性

```sh
python3 -B crates/an-agent-host/tests/cli/native_binary.py \
  --host /selected/an-agent-host --evidence /private/tmp/native-binary-NEW
```

真实的 macOS 套件检查缺失/不匹配的运行时拒绝，变更依赖拒绝在启动前和接受，只读运行时强制执行，新版本发布后 opaque byte 的传递，确认取消，主动收集和取消输出接受拒绝，以及在不使用 Python 的情况下保留产品/重复确认。

它会私下记录命令和证据，且从不重新构建其选定的二进制文件。

Loom 单独打包现有的日志报告代码，并验证真实可编辑的 XLSX/PPTX 产品。不提供 GUI、模型、GPU 或新的后端。

为了实现客户端独立执行原生文件输入尝试，使用 `spool-supervisor start`。其单独的工作者在客户端突然退出后仍保留原始截止时间和进程所有权。[监督合同](../../session-and-retention.md#independent-attempt-supervisor) 定义了持久启动、取消和不确定结果的保留。原生 CLI 事件传递、群体调度和对等阶段也使用独立的 [执行所有者](../../session-and-retention.md#routed-execution-ownership)。普通 `spool-start` 保留其前台行为。
